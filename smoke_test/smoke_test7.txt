2. PHASE 1 — DIAGNOSIS: THE DUPLICATES WERE NOT DUPLICATES
================================================================================

2.1 The reported symptom
--------------------------------------------------------------------------------
scan 117 — quickscan against pentest-ground.com, 2026-07-25 14:13:20:

    1. [CRITICAL] port 80 — Redis is an open source, in-memory database...
    2. [CRITICAL] port 80 — Redis is an open source, in-memory database...
    3. [HIGH    ] port 80 — Redis is an open source, in-memory database...
    4. [HIGH    ] port 80 — Redis is an open source, in-memory database...

Two identical-looking CRITICAL rows, two identical-looking HIGH rows, in one
report. Reported as duplicate findings.

2.2 Three hypotheses, all tested, all rejected
--------------------------------------------------------------------------------
(a) "The renderer's SELECT is scoped by target, not scan_id, so findings
     from this target's many prior scans (105, 110, 111, 116...) bleed in."
    REJECTED. database/db.py:152-155 is verbatim:
        SELECT * FROM findings WHERE scan_id = ?
    Scoped by scan_id. No target-scoped read exists anywhere in the
    findings-retrieval path.

(b) "A one-to-many JOIN with a CVE-enrichment or tags table fans out."
    REJECTED. There is no JOIN anywhere in the retrieval path, and no table
    to join to — the schema is two tables (scans, findings), and enrichment
    is written into columns on the finding row itself at insert time. A fan-
    out is not structurally possible.

(c) "The Redis template fires twice in one run — e.g. two fuzzed candidate
     URLs both landing on the same probe."
    REJECTED, and this is where the real answer came from. Raw tool output
    for scan 117, from output/pentest-ground.com/scan_errors.log:782-787:

        template_id: CVE-2025-46817   severity: critical
        template_id: CVE-2025-49844   severity: critical
        template_id: CVE-2025-46818   severity: high
        template_id: CVE-2025-46819   severity: high
        template_id: redis-default-logins    severity: high
        template_id: exposed-redis           severity: high

    SIX DISTINCT nuclei templates. Six distinct findings. Six distinct rows
    in the database (ids 5408-5413). Nothing was duplicated at any layer.

2.3 The actual defect — a truncation collision
--------------------------------------------------------------------------------
The four CVE templates' descriptions are upstream nuclei prose, and all four
open with the SAME 160-character sentence:

    "Redis is an open source, in-memory database that persists on disk.
     Versions 8.2.1 and below allow an authenticated user to use a specially
     crafted Lua script to ..."

...and only then diverge into "cause an integer overflow", "manipulate the
garbage collector", "read out-of-bound data", "manipulate different LUA
objects".

report_txt.py truncated the description to 60 characters
(_TOP_FINDING_DESC_MAXLEN) for the at-a-glance list. Below 60 characters the
four are byte-identical. Four different RCE/DoS bugs, one visible row shape.

Reproduced in a unit test before any fix was written (t_phase2.py case D):
    BEFORE fix: 4 Redis CVEs collide at 60 chars    PASS (bug reproduces)
    AFTER  fix: all 6 truncate to DISTINCT strings  PASS

2.4 Why the disambiguator was missing — the real data bug
--------------------------------------------------------------------------------
_finding_identifier() prefers cve_id and only falls back to a truncated
description. cve_id would have made these four instantly distinct. It was
NULL for all four.

Cause, verified against the template on disk
(/home/jafar/nuclei-templates/javascript/cves/2025/CVE-2025-46817.yaml):

    id: CVE-2025-46817          <-- the CVE is the template id
    info:
      name: Redis < 8.2.1 lua script - Integer Overflow
      severity: critical
      # NO classification: block at all

nuclei_wrap.py read info.classification.cve-id, which none of the four
templates define. The CVE identifier was sitting unread in template_id the
whole time.

Confirmed across all four: none has a classification block. Confirmed by
capturing REAL nuclei JSONL against pentest-ground.com rather than trusting
the YAML — see 2.5.

2.5 Two further real defects, found by capturing raw nuclei output
--------------------------------------------------------------------------------
Rather than reason from the templates, a real nuclei run was captured:

    nuclei -u http://pentest-ground.com -severity critical,high -jsonl

    template-id : CVE-2025-46819
      type      : javascript
      matched-at: pentest-ground.com:6379
      port      : 6379                       <-- NOT 80
      classification : None

    template-id : exposed-redis
      port      : 6379
      classification : {'cve-id': None, 'cwe-id': ['cwe-306'],
                        'cvss-score': 7.2}   <-- a real score, never read

  (i) WRONG PORT. The Redis Lua templates hardcode Port "6379" and pivot
      there regardless of the URL they were launched against. nuclei
      reported port 6379. Aegis recorded port 80 — the web port the wrapper
      had been pointed at. Four Redis flaws were being attributed to the
      web server. This was not in the bug report; it was found by looking
      at the tool's own output.

 (ii) UNREAD CVSS. exposed-redis publishes classification.cvss-score 7.2.
      The wrapper never read cvss-score, so every nuclei finding rendered
      "not scored" regardless of what nuclei actually supplied.

2.6 Phase 1 conclusion
--------------------------------------------------------------------------------
Not a scan_id scoping bug. Not a JOIN fan-out. Not a double-fire. The
defects were:
    - cve_id never populated when the template id IS the CVE
    - findings attributed to the probed port, not the matched port
    - published CVSS scores discarded
    - and a report that truncated four different findings into one shape

Bearing on Phase 2, stated plainly: the requested dedup key
(finding_type, port, description, tool) uses the FULL description, so it
correctly collapses nothing here. Had it been keyed on the *rendered*
(truncated) string — which is what the symptom looked like it called for —
it would have silently destroyed CVE-2025-49844, -46818 and -46819 from
every report. Confirmed by test (t_phase2.py case F).


3. PHASE 2 — FIXES + DEFENSIVE DEDUP
================================================================================

3.1 Root-cause fixes (collection time)
    modules/web/nuclei_wrap.py
      + _cve_from_template() — prefers info.classification.cve-id; falls
        back to a CVE-shaped template id (anchored regex, case-insensitive).
        Nothing invented: a non-CVE-shaped id like "exposed-redis" still
        yields None.
      + _cvss_from_classification() — reads classification.cvss-score,
        discarding non-numeric or out-of-range values.
      + _matched_port() — nuclei's own `port`, falling back to parsing
        matched-at, falling back to None (which preserves the old
        behaviour).
      + result dicts gain matched_port, protocol, scheme.

    modules/profiles/_common.py
      + nuclei_description() — folds the template NAME onto the front of
        the description. db.py has no column for a template name, so a name
        passed through the mappers is dropped at insert; putting it in the
        description is what makes it survive the round-trip, using a column
        that already exists. Both halves are nuclei's own output.
      + nuclei_port() / nuclei_service() — shared by both profiles that map
        nuclei findings, so quickscan and deepscan cannot drift.
        nuclei_service() deliberately returns None for tcp/javascript
        templates rather than inferring "redis" from port 6379: a port
        convention is not an observation.

    modules/profiles/quickscan.py, deepscan.py
      + both nuclei mappers now carry port (matched), service, cvss, name.

3.2 Defensive dedup — added, and it turned out NOT to be a no-op
    modules/reporting/summary.py
      + deduplicate_findings(), keyed on
        (finding_type, port, cve_id, severity, description)
        — the FULL description, never a rendered one. cve_id and severity
        are in the key beyond the requested four so the pass stays
        conservative.
      + wired into build_summary(), the single chokepoint both the txt and
        PDF writers consume, so the two can never disagree on how many
        findings a scan had.
      + every collapse is logged AND printed, naming the finding and the
        number of copies dropped. A de-duplicator that quietly deletes rows
        from a security report is a worse defect than the duplication it
        guards against.

    It was built as a guard against a hypothetical. It caught a real one on
    its first deepscan run — see 3.4, which is the most useful single result
    in this pass after the Phase 1 diagnosis.

3.4 A REAL duplicate-insert path, found by the new guard (scan 127)
--------------------------------------------------------------------------------
deepscan/pentest-ground.com printed:

    [!] [Summary] collapsed 1 duplicate finding row(s)
    [!] [Summary] duplicate collapsed: Redis - Default Logins — ...
        (type=nuclei_finding, port=6379, severity=HIGH)
        — 1 extra copy(ies) dropped, 1 kept

Database showed 77 rows against 76 rendered, with ids 5500 and 5525 both
"Redis - Default Logins" on port 6379.

Cause: deepscan runs nuclei ONCE PER WEB PORT. This host has 80 and 443
open, and the Redis templates pivot to 6379 regardless of the URL they were
launched against — so the same match came back from both probes.

Crucially, this duplicate was CREATED BY the matched-port fix in 3.1. Before
it, the two copies recorded port 80 and port 443 and read as two different
findings — wrong, but not duplicated. Recording the true port made them
genuinely identical. A fix that surfaced a latent second bug, and the guard
built in the same pass is what caught it.

Fixed at the source as well as at render time:
    modules/profiles/deepscan.py
      + _findings_from_nuclei() takes a `seen` set of
        (template_id, matched_port) pairs, shared across the per-port web
        loop, so a pivoting template is recorded once and the skip is
        announced. quickscan does not need this — it probes a single port.

    Unit-verified: same template from :80 and :443 -> 2 findings, not 4;
    same template on 6379 vs 6380 -> still 2, correctly kept separate.

    Confirmed live by scan 128 (deepscan re-run, post-fix):
        database rows 82   report total 82   nuclei findings exactly 6
        no dedup collapse message — nothing left to collapse
    Stated honestly: the cross-port collision did not RECUR in 128, because
    nuclei matched the Redis templates from the :80 probe only that run. The
    fix is proven by unit test and the end state is proven live; the exact
    live collision was not re-triggered.


3.3 Verified NOT to merge legitimately different findings (Phase 2 item 3)
    All PASS (t_phase2.py section F):
      same CVE on two different ports                    -> stays 2
      two different CVEs with identical description      -> stays 2
      different finding_type, identical description      -> stays 2
      different severity, identical description          -> stays 2
      descriptions differing ONLY past char 60           -> stays 2   <-- the
                                                            decisive case
      genuinely identical rows                           -> collapses to 1
      triplicate                                         -> collapses to 1
      real scan 117 rows: 9 in                           -> 9 out
    Input list and dicts are never mutated (verified).


4. PHASE 3 — HONEST FIELD RENDERING
================================================================================

4.1 The two states a bare "-" was hiding
    modules/reporting/summary.py
      + FINDING_TYPE_TOOL — which tool produced each finding type.
      + _NOT_APPLICABLE — per (field, finding_type) reasons a field cannot
        apply by nature.
      + field_display() returns, in order: the value; "N/A (<why>)" when the
        field cannot apply; "not determined by <tool>" when it could have
        and nothing filled it in. It never returns a bare dash.
      + service_display() — never drops a half-known pair: a known service
        with no version renders "nginx (version not determined by nmap -sV)".
      + cvss_display() — says whether a grade came from CVSS or the
        heuristic.

    Examples now rendered:
        missing_security_header / CVE   -> "N/A (config finding)"
        discovered_path / CVE           -> "N/A (path discovery)"
        sqlmap_finding / CVE            -> "N/A (injection class, not a CVE)"
        smb_share / Service             -> "N/A (host-level finding)"
        nuclei_finding / Service        -> "not determined by nuclei"
        nikto_finding / CVE             -> "not determined by nikto"

4.2 Populated at the source where the tool really did know (Phase 3 item 1)
    The brief asked specifically whether the Redis wrapper sets a service
    field. It does not, and it should not — nuclei's `type` for those
    templates is "javascript"/"tcp", a protocol class, not a service name.
    What nuclei DID determine and Aegis was discarding was the PORT (6379)
    and, for exposed-redis, the CVSS score (7.2). Both are now read from the
    tool's own output. Nothing is guessed.

4.3 Shared between txt and PDF so they cannot disagree
    finding_identifier() moved into summary.py. The PDF previously fell
    straight through to a service label and titled EVERY nuclei match
    "unknown"; the text report had a description fallback. Same finding, two
    different names depending which file you opened. One implementation now.

4.4 Render-time collision repair — needed for scans already in the database
    Discovered during Phase 7, not predicted: the collection-time fixes
    cannot reach rows already stored. Re-rendering scan 111 still produced
    four identical-looking rows, because its cve_id is NULL and its
    description is the bare upstream prose.

    + distinct_identifiers() resolves collisions at render time:
        1. append the text where the group actually DIVERGES. Showing more
           of the description does not work — the four Redis templates share
           their first ~160 characters, so a wider window is still four
           identical strings, only longer. The distinguishing text lives
           immediately past the common prefix, so that is what is appended.
        2. if descriptions are byte-identical, distinguish by port and type
        3. and failing that, a positional marker, so the guarantee is
           unconditional
      A group that shares a SERVICE label ("http 1.31.3" on ports 80/81/443)
      is deliberately left alone — those rows are already told apart by the
      port printed beside them, and appending "…80." / "…81." would restate
      the adjacent column as noise. (This gate was added after the first
      implementation regressed exactly that case; caught in Phase 7.)

    Result, scan 111 (historical rows, unchanged in the database):
      1. [CRITICAL] Redis is an open source... …ua script to manipulate the
                                                 garbage collec...
      2. [CRITICAL] Redis is an open source... …ua script to cause an integer
                                                 overflow and...
      3. [HIGH    ] Redis is an open source... …UA script to read out-of-bound
                                                 data or cra...
      4. [HIGH    ] Redis is an open source... …ua script to manipulate
                                                 different LUA obje...

    Verified across the WHOLE database: all 120 scans render unique
    top-finding lines and detail cards distinguishable by
    (label, severity, port).


5. PHASE 4 — CAPPED, INDEXED REPORT RETENTION
================================================================================
New module: modules/reporting/retention.py

5.1 Filename scheme
    report_<profile>_<target>_<scan_id>.txt / .pdf
    e.g. report_deepscan_scanme.nmap.org_115.txt
    The profile is in the filename so a directory listing says what each
    report IS without opening it.

5.2 Cap: 5 per profile+target  (confirmed with the user before building)
    Each profile keeps its own budget for a given target, so a burst of
    quickscans cannot evict the one deepscan report of that host — which a
    flat per-target cap would do, and which is the exact evidence loss this
    module exists to prevent.

5.3 Interactive prompt, all three choices
    Delete oldest [o] / delete by number / keep all [k]. Invalid input
    re-prompts rather than crashing or silently defaulting. Ctrl+C / EOF is
    read as "keep everything" — an interrupted operator has not consented to
    a deletion.

5.4 Non-interactive
    --non-interactive flag added to aegis.py, plumbed through all five
    profiles. Also implied automatically when stdin/stdout is not a TTY, so
    a piped or scheduled run never hangs on a prompt. The choice and the
    REASON are logged and printed.

5.5 Pruning never risks the report just written
    Runs only AFTER the new report is on disk; the newest report is never a
    deletion candidate; every failure is caught and logged rather than
    raised. Legacy fixed-name report.txt/report.pdf are deliberately NOT
    swept up — they belong to no identifiable scan, so the pruner will not
    delete what it cannot account for. (Verified: both still present in
    output/pentest-ground.com/ after this pass.)

5.6 Prunes to the cap, not one file per run
    Found in Phase 7: the first implementation deleted exactly one report
    per scan, so a directory that started over-cap (reports re-rendered by
    hand, or restored) took several scans to converge. Now loops to the cap.
    "Keep all" still ends pruning immediately — asking again after the user
    has just declined would be badgering.
    Verified: 8 stored, cap 5 -> 3 deleted in one run, newest always kept.

7.2 SQLi/XSS discovery ordering — CLOSED, and it was worse than documented
    It was recorded as an ordering problem. It was not: _common.
    web_param_candidates() iterated PARAMETERS in the inner loop and
    returned as soon as the cap was hit, so the FIRST discovered endpoint
    consumed the entire 6-candidate budget. Reproduced:

        BEFORE: 6 candidates, ALL on /index.php
                DISTINCT endpoints fuzzed: 1
                (/xss.php and /info.php never fuzzed at all — no reordering
                 alone could have fixed this)

    Two bounded changes, same budget, no extra requests:
      - parameters iterated in the OUTER loop, so every endpoint gets its
        first parameter before any endpoint gets its second
      - endpoints ranked by _endpoint_rank(): names suggesting a query
        parameter (search/info/xss/id/view/...) first, site roots
        (index/home/default) last. A hint for ORDER only — nothing is ever
        excluded, so a parameterised /index.php is still fuzzed.

        AFTER:  DISTINCT endpoints fuzzed: 4
                ['index.php', 'info.php', 'search.php', 'xss.php']
                xss.php and info.php now reached FIRST.
    Regression-checked: empty/None input, 404 exclusion, non-script
    exclusion, cap respected, dedup across gobuster+dirb, return shape.

7.4 TWO NEW instances of the documented skip-flag convention violation
    Found while verifying 7.3, by auditing every module rather than only
    the two named:

    modules/web/header_check.py — a LIVE false-failure bug, same class as
      zap_wrap.py in smoke_test5 §5.5. It drives requests through
      safe_call() rather than run_tool(), and safe_call reports a
      KeyboardInterrupt as an ordinary error string. header_check set
      result['error'] and never set result['skipped'], so a deliberate
      Ctrl+C was counted as a FAILED tool — and, since smoke_test5's
      reporting change, PRINTED as one.

    modules/scanning/banner.py — not miscounted (its per-port errors never
      reach result['error']) but a skip there was entirely INVISIBLE:
      not counted failed, not counted skipped, nothing on the summary panel.
      It now records the skip and stops probing the remaining ports rather
      than making the operator interrupt once per port.

    Root cause of the recurrence addressed, not just the two instances:
      modules/utils/error_handler.py
        + SKIP_REASON_INTERRUPT / SKIP_REASON_SKIP_KEY constants (the two
          reasons were previously bare string literals at their use sites)
        + is_user_skip() — the single place that recognises a deliberate
          skip, for the modules that replicate run_tool()'s contract by hand.
      This is the third time this bug has appeared (zap_wrap, header_check,
      banner). It now has one shared test instead of three hand-written ones.

9. HONEST LIMITATIONS
================================================================================
 1. Historical database rows are NOT rewritten. Scans recorded before this
    pass still carry NULL cve_id and port 80 for the Redis findings. Their
    REPORTS now render unambiguously (4.4), but the stored data is
    unchanged. This was a deliberate choice: silently rewriting recorded
    scan results would destroy the evidentiary record, which is the same
    failure mode Phase 4 exists to prevent. A backfill would be a separate,
    explicit operation.

 2. Service is still "not determined by nuclei" for the Redis findings.
    nuclei genuinely does not report a service name for tcp/javascript
    templates — only a protocol class. Inferring "redis" from port 6379
    would be a convention, not an observation, and the brief was explicit
    that a value should not be invented.

 3. The "not determined by <tool>" label is honest but repetitive on
    web-heavy scans: gobuster/nikto/zap findings do know their scheme
    (http vs https) at wrapper level, and that could be populated at the
    source the way nuclei's port now is. Only nuclei was fixed this pass —
    it was the wrapper named in the brief. The other web wrappers are a
    known, documented gap, not an oversight.

 4. Two runs per profile per target was NOT achieved for every pair.
    Achieved: quickscan/pentest-ground.com x3 (118, 119, 126);
              deepscan/pentest-ground.com x2 (127, 128).
    Single post-fix run: stealthscan, compliance, webaudit on
    pentest-ground.com; stealthscan, compliance, quickscan on
    scanme.nmap.org. Repeats were spaced rather than stacked to respect the
    rate-limiting behaviour smoke_test5 documented.

 9. The cross-port nuclei dedup (3.4) is proven by unit test and by scan
    128's correct end state, but the live collision did not recur in 128 —
    nuclei matched the Redis templates from the :80 probe only that run. A
    third deepscan where both probes match would exercise the live path
    again; it was not run.

 5. webaudit and deepscan were NOT re-run against scanme.nmap.org this
    pass. They were verified there in smoke_test5 (scans 109, 115) and
    nothing in this pass changes their scanning behaviour — only reporting,
    which is exercised by the eight scans that did run. Stated so the
    matrix is not read as more complete than it is.

 6. The retention prompt's interactive path is proven by a pty harness,
    not by a human typing at it. The harness uses a real TTY (isatty True
    on both streams) and real keystrokes, so the gate and the parsing are
    genuinely exercised, but it is still an automated test.

 7. distinct_identifiers() resolves collisions among the findings PASSED TO
    IT — the top-findings list and the detail list separately. It does not
    guarantee uniqueness against findings from a different scan, which is
    not a case any report renders.

 8. The severity of scan 122 (webaudit/pentest-ground.com) is 6 MEDIUM /
    24 LOW with no HIGH or CRITICAL, whereas quickscan found 2 CRITICAL on
    the same host. That is expected — webaudit does not run the nuclei
    severity pass that finds the Redis CVEs — but it does mean a webaudit
    report alone understates this host's risk. Pre-existing profile-scope
    behaviour, not introduced here, and not changed.

10. FINAL VERDICT
================================================================================
The reported bug did not exist. Four rows that looked identical were four
different Redis remote-code-execution CVEs that the report could not tell
apart, because it truncated their descriptions to 60 characters and the four
share their first 160. Acting on the symptom as described — collapsing the
"duplicate" rows — would have permanently deleted CVE-2025-49844,
CVE-2025-46818 and CVE-2025-46819 from every report Aegis produces.

What was genuinely broken, all fixed and verified:
  - cve_id never populated when the nuclei template id IS the CVE
  - findings attributed to the probed port instead of the port nuclei
    actually matched on (four Redis flaws credited to the web server)
  - published CVSS scores read from nuclei and discarded
  - reports that could not distinguish four different findings
  - a bare "-" standing for both "cannot apply" and "nobody determined it"
  - the PDF titling every nuclei finding "unknown" while the text report
    did not — same finding, two names
  - reports overwritten per target, with no history and no warning
  - no end-of-run statement of what was found or where the report went
  - XSS fuzzing that spent its entire candidate budget on the first
    endpoint, so xss.php was never fuzzed at all
  - header_check.py counting and printing a deliberate Ctrl+C as a tool
    failure — the third instance of a documented non-negotiable convention
    being violated, now with a shared constant and helper so it is the last
  - banner.py making a user skip completely invisible
  - config.example.py missing four keys a fresh install needs

Two findings came out of the work rather than the brief, and both are worth
more than the items that were asked for:
  - nuclei reports a matched port that differs from the probed port; Aegis
    was discarding it (2.5)
  - the defensive dedup pass, built as a guard against a hypothetical,
    immediately caught a real duplicate-insert path in deepscan that the
    matched-port fix had itself created (3.4)

Evidence: 123 unit assertions, 11 pty assertions, 11 real scans across all
five profiles and both targets with zero tool failures, and a mechanical
audit of every report written. Every previously-open coverage gap from
smoke_test5/6 is closed — webaudit and deepscan against pentest-ground.com
both ran to completion for the first time.

Limitations are stated in section 9 and are real: historical database rows
are not rewritten, service remains undetermined for the Redis findings
because nuclei genuinely does not report one, the other web wrappers still
do not populate service, and repeat coverage is uneven across profiles.
