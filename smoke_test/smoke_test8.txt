2.2 The distinction that drove the decision
--------------------------------------------------------------------------------
The two corrections are not the same kind of operation, and saying so was the
most useful part of this phase:

    cve_id is RECOVERED. output/<target>/scan_errors.log recorded the
    template_id verbatim at scan time —
    output/pentest-ground.com/scan_errors.log:226 is:
        Finding recorded: {'type': 'nuclei_finding', 'port': 80,
        'template_id': 'CVE-2025-46819', ...}
    The value was observed during that run and written down. Restoring it to
    the row is recovering an observation.

    port would be INFERRED. Port 6379 does not appear in ANY log before
    2026-07-25 15:59:38 — which is scan 126, AFTER the smoke_test7 fix. For
    the six older scans the matched port was never recorded anywhere. Writing
    6379 in would not restore an observation; it would derive a value from
    the template's pivot behaviour and put it into a historical record that
    nothing from that run attests to. The SSH rows are weaker still: there is
    no post-fix run against scanme.nmap.org to corroborate Port 22 at all.

2.4 How the migration establishes what a row's template was
--------------------------------------------------------------------------------
tools/backfill_nuclei_identity.py. Standalone and explicitly invoked —
nothing in the scanner calls it, it is not wired into startup or any profile,
and it is dry-run unless --apply is passed.

A row is only updated when TWO INDEPENDENT derivations of its template id
agree:

  (1) positional — the scan's nuclei log events, taken within that scan's own
      time window, paired in order with that scan's nuclei rows. Accepted
      only when the counts match AND every paired severity matches.
  (2) textual — the row's description prose mapped to a template name (via
      the '<name> — <prose>' form post-fix rows store), and thence to a
      template id via the logs.

Both mappings were verified unambiguous against the real data before use:
10 distinct template names, 0 mapping to more than one template id; 6
distinct prose bodies, 0 mapping to more than one name.

Where they disagree, or either is unavailable, the row is SKIPPED and named
in the dump. Two rows were skipped on that basis (5106, 5107 — scan 89,
172.28.0.20): that target's nuclei events are not in the log, and no post-fix
run of those templates exists to derive them textually. Row 5107 is a
configuration-listing finding whose twins in scans 90 and 112 DID receive
cvss 5.3; it keeps NULL. That inconsistency is the honest outcome of
declining to guess, and is preferred to a tidier database.

Two scans failed positional pairing and fell back to textual evidence alone:
    scan 71  — scan 72 (compliance) was registered 59 MICROSECONDS later
               against the same target, so the time window closes instantly.
               The guard correctly refused to pair rather than reaching into
               a neighbouring scan's events.
    scan 89  — no nuclei events in the log for that target/window at all.

3. PHASE 2 — WHAT THE OTHER WEB WRAPPERS WERE DISCARDING
================================================================================

smoke_test7 §9.3 recorded this gap as "gobuster/nikto/zap know their scheme
and could populate it". The audit found the scheme was the smallest part of
it.

3.1 Method: real tool output, captured and inspected
--------------------------------------------------------------------------------
No field was added on the strength of a tool's documentation. Each tool was
run and its raw output inspected, against the local DVWA fixture so the
public targets' rate limits were not spent on format inspection. The captures
are committed as test fixtures so the assertions are reproducible:

    tests/fixtures/gobuster_raw.txt      gobuster vs http://127.0.0.1:8082
    tests/fixtures/nikto_raw.txt         nikto 2.6.0 vs 127.0.0.1:8082
    tests/fixtures/zap_alerts_raw.json   ZAP, 25 real alerts
    tests/fixtures/nuclei_raw.jsonl      carried over from smoke_test7

3.2 gobuster — Size and redirect target were never parsed
--------------------------------------------------------------------------------
Real output:
    docs         (Status: 301) [Size: 312] [--> http://127.0.0.1:8082/docs/]
    index.php    (Status: 302) [Size: 0]   [--> login.php]
    favicon.ico  (Status: 200) [Size: 1406]

_RESULT_LINE stopped at the status code, so [Size:] and [--> ...] were
matched by nothing and discarded. Both are real, tool-reported detail: the
size distinguishes a 0-byte stub from a real page, and the redirect target
says where a 301 actually goes. Both are now parsed, with both groups
optional so a build that omits either still parses rather than silently
yielding zero paths.

3.3 dirb — SIZE was already captured, then dropped on the floor
--------------------------------------------------------------------------------
_FOUND_LINE has always had a (?P<size>\d+) group. The dict built two lines
later was {path, status_code}. The value was parsed and then discarded at the
point of use — the shortest possible distance between having data and losing
it. Now kept. Directory hits, which dirb reports without a SIZE, keep None
rather than a fabricated 0.

3.4 nikto — test id, affected URI, citation and server banner
--------------------------------------------------------------------------------
Real output:
    + Server: Apache/2.4.25 (Debian)
    + [013587] /: Suggested security header missing: referrer-policy. See: ...
    + [750500] /config/: Directory indexing found.
    + [600050] Apache/2.4.25 appears to be outdated (current is at least ...)

  - the test id ([95], [013587] — the width varies) is nikto's own identifier
  - the URI prefix is the path the finding concerns
  - "See: <url>" was ALREADY parsed into `reference` and then dropped at
    insert, because there was no column for it (see 3.6)
  - "Server:" was filtered out as metadata, but it is nikto's own observation
    of the server banner and the only place the product/version appears

The fourth line is why the path is matched with a leading "/" only:
"Apache/2.4.25 appears to be outdated" has no URI, and a looser pattern would
have recorded "Apache/2.4.25" as one. Verified by test.

"Server: No banner retrieved" is treated as no banner rather than as a
product called "No banner retrieved".

3.5 ZAP — keeping 4 fields out of ~20, including its own remediation
--------------------------------------------------------------------------------
The largest gap by far. Field census over a real 25-alert run:

    100% populated : alert, description, solution, reference, url, cweid,
                     confidence, method, risk, pluginId, alertRef
     68% populated : evidence   (17/25)
     52% populated : param      (13/25)
      0% populated : attack, inputVector

The wrapper kept rule_id, name, status and severity. It discarded ZAP's own
description, its per-alert remediation advice, the URL it matched at, the
evidence string and the parameter — five fields for which the findings table
has had columns for some time.

Now carried. Fields ZAP left empty stay empty: `attack` is 0/25 because a
passive baseline scan sends no attack payloads, and param/evidence are
genuinely absent on some rules. Those render "not determined by zaproxy"
rather than a fabricated value.

    cweid -1 is ZAP's own "not applicable" sentinel — Session Management
    Response Identified carries it. Rendering that as "CWE--1" would invent a
    weakness class that does not exist, so <= 0 is dropped.

    ZAP reports one alert per matching URL; 25 alerts are 9 distinct rules.
    The collapse keeps the first URL as exemplar and records how many URLs
    matched, so "(matched at 4 URLs)" appears rather than the breadth being
    silently lost.

3.6 One new column: reference
--------------------------------------------------------------------------------
nikto, ZAP and wpscan all parsed a citation URL and all three lost it at
insert for want of a column. Added via db.py's existing, documented
ALTER TABLE migration pattern — safe to re-run, existing rows simply carry
NULL. A citation is neither evidence of a finding nor remediation for it, so
it gets its own column rather than being folded into either.

3.7 Scheme, handled properly rather than as a scheme field
--------------------------------------------------------------------------------
The brief named http-vs-https. Rather than a bare `scheme` column, the
wrappers populate `endpoint` with the full URL — which carries the scheme,
the port AND the path, in a column that already existed. gobuster composes it
from the base URL it was launched against; dirb reports absolute URLs itself;
nikto gets base_url + the URI it flagged (findings with no URI get the base
URL, which is still true of them); ZAP reports `url` directly.

3.8 nuclei's matched-at — found while verifying the above
--------------------------------------------------------------------------------
Not in the brief. With Endpoint rendering for the first time, nuclei findings
read "Endpoint: not determined by nuclei" — while nuclei_wrap had been
parsing `matched-at` since smoke_test7's matched-port fix and the mappers
were dropping it. Verified against the real JSONL fixture: every one of the
six Redis matches carries 'pentest-ground.com:6379'. Now mapped to endpoint
in both profiles that map nuclei findings.

Reported honestly: this was a one-line fix to close a gap that the pass's own
new column had made visible. It is scope creep of the smallest kind, and it
is recorded rather than folded in quietly.

4. THREE DEFECTS FOUND BY THIS WORK
================================================================================

4.1 A tool's own remediation was being overwritten with generic text
--------------------------------------------------------------------------------
enrichment/remediation.py:482 read:

    enriched["remediation"] = remediation_text(enriched)

— unconditionally. So once the ZAP wrapper started supplying ZAP's per-alert
`solution`, enrichment immediately replaced it. Rendered result:

    ZAP's own text : "Ensure that the HttpOnly flag is set for all cookies."
    what was shown : "Review the ZAP baseline alert 'Cookie No HttpOnly Flag'
                      against OWASP guidance for that alert class and
                      remediate the underlying misconfiguration."

The second sentence tells the reader to go and look it up; the first is the
answer. A tool-supplied remediation now wins over the generic text; an empty
or whitespace-only one still falls back exactly as before. Only findings
whose wrapper genuinely populates the field are affected — a grep confirmed
the ZAP mapper is the only one that does.

4.2 A REGRESSION THIS PASS INTRODUCED, AND HOW IT WAS CAUGHT
--------------------------------------------------------------------------------
This is the most important entry in this file.

Both enrichment/severity.py::_finding_type and
enrichment/remediation.py::_finding_kind sniff a finding's kind from its
shape when no type is declared. Both contained:

    if finding.get("description") is not None and "reference" in finding:
        return "nikto_finding"

— keyed on the KEY BEING PRESENT. Rows read back from SQLite carry every
column in the table. Adding the `reference` column (3.6) therefore made that
condition true for EVERY stored row, and every described finding with no
declared type started classifying as a nikto finding.

Observed live, scan 131 (stealthscan / pentest-ground.com), on an OPEN PORT
finding:

    Description   : Http is exposed on port 80.
    Remediation   : Review this nikto finding against the application's
                    intended configuration and ...

nikto does not run in stealthscan. The report was naming a tool that never
executed, for a finding it never produced.

Root-caused rather than patched at the symptom. Two things were wrong:

  (a) both classifiers read only `type`, never `finding_type` — which is the
      column name db.py actually persists under. Every stored row was being
      put through shape-sniffing despite already declaring what it was. Both
      now honour `finding_type`, so a stored row is read, not guessed at.
  (b) the nikto heuristic now requires a TRUTHY reference, not a present key.

    Fixed, verified on the same scan:
        Remediation   : Redirect all HTTP traffic to HTTPS and serve the site
                        over TLS so credentials and sessions are not sent in
                        the clear.

Stated plainly, because it bears on how much the other evidence in this file
proves: THE WHOLE-DATABASE SWEEP PASSED STRAIGHT THROUGH THIS BUG. That sweep
checks for ambiguous cells, duplicate top-finding lines and crashes across
every scan. A confidently-worded, entirely wrong remediation sentence is none
of those things. It was found by reading one rendered report, and by nothing
else. 187 findings across five profiles carry a NULL finding_type and were in
scope of the defect.


4.3 A CVE duplicate-insert path in deepscan — found, documented, NOT fixed
--------------------------------------------------------------------------------
The dedup guard smoke_test7 built fired on two of this pass's deepscans, on
two different hosts:

    scan 130 (172.28.0.20)      duplicate collapsed: CVE-2016-8743
                                (type=cve, port=80, severity=HIGH)
    scan 138 (scanme.nmap.org)  duplicate collapsed: CVE-2021-44224
                                (type=cve, port=80, severity=HIGH)

Cause, from the run's own console output (scan 138):

    [*] [CVE] Querying NVD for 'Apache httpd 2.4.7'          <- service detect
    [*] [CVE]   CVE-2021-44224 — CVSS 8.2 (HIGH)
    [*] [CVE] Querying NVD for 'apache http server 2.4.7'    <- header fingerprint
    [*] [CVE]   CVE-2021-44224 — CVSS 8.2 (HIGH)

deepscan enriches CVEs down two independent paths — nmap's detected service
product, and the Server header's product — and on a host where both name the
same software, both queries return the same CVE and BOTH are inserted. Same
class as smoke_test7 §3.4's nuclei duplicate, different producer.

Reports are CORRECT: the render-time guard collapses it and says so out loud,
which is exactly the job it was built for. The database row is still
duplicated, which is why db and rendered counts differ by one on those two
scans (§6.4).

Deliberately NOT fixed in this pass. The fix belongs at collection time in
deepscan's CVE enrichment, and by the time it was diagnosed both live
deepscans had already run; changing enrichment behaviour without a live
deepscan to re-verify it would mean shipping an unverified collection-time
change on the strength of a unit test alone, which is the opposite of how
every other fix in this pass was handled. Reproduced on two independent
hosts, so it is not target-specific and will keep occurring until fixed.
Carried into §9.10 as an open item rather than closed quietly.

5. PHASE 4 — WEBAUDIT SCOPE DISCLOSURE
================================================================================

smoke_test7 §9.8 noted that webaudit on pentest-ground.com reported 6 MEDIUM
/ 24 LOW while a quickscan of the same host found 2 CRITICAL, and that
nothing in the webaudit report explained why. Not a bug — that is the
profile's designed scope — but a report silent about its own scope reads as a
statement about the host rather than about the scan.

5.1 The claim was checked before it was written
--------------------------------------------------------------------------------
The obvious wording — "webaudit does not run nuclei" — is FALSE. webaudit
runs nuclei in `-dast -tags xss` mode for reflected XSS. What it does not run
is the severity template pass over the host's other exposed services. The
note says exactly that:

    Scope: this profile audits the web application layer. It runs nuclei only
    in DAST mode for reflected XSS, not the severity template pass that
    quickscan and deepscan run against the host's other exposed services — so
    CVE-class findings on non-web ports are outside what this report covers.
    A quickscan or deepscan of the same host may surface findings this report
    does not.

5.2 One source, three surfaces
--------------------------------------------------------------------------------
summary.profile_scope_note() is the single definition; the text report, the
PDF cover and the end-of-run CLI banner all read it, so the three cannot
drift into describing the same profile's scope differently. Placed directly
under the header, not at the end: a reader who stops after the severity
summary is exactly the reader who needs it.

5.3 Verified
--------------------------------------------------------------------------------
    - renders on scan 122, the exact 6 MEDIUM / 24 LOW report that motivated it
    - absent from quickscan/deepscan/stealthscan/compliance reports
    - present in the PDF cover HTML for webaudit, absent for deepscan
    - case-insensitive, and safe for an unknown or None profile
    - live webaudit runs in section 6 confirm it end to end
