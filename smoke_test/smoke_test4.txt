ITEM 2 — sqlmap (condition: injectable_param_found)
--------------------------------------------------------------------------------
STATUS: CONFIRMED WORKING via both paths — real end-to-end dispatch, AND a
real confirmed injection — but this is the one item with a genuine,
newly-diagnosed architecture gap worth flagging (not fixed this pass, by
design — see below).

dvwa-target: `vulnerables/web-dvwa` (self-contained, own MariaDB), database
created via its own unauthenticated setup.php, security level set to low by
logging in as DVWA's own default admin/password account.

Root-cause investigation (confirmed live, not assumed): DVWA's real SQLi
lab page (vulnerabilities/sqli/index.php) sits behind DVWA's PHP-session
login wall. modules/web/sqlmap_wrap.py's run_sqlmap() builds
`sqlmap -u <url> --batch --random-agent --level 1 --risk 1` with NO
--cookie support. That means Aegis's real unauthenticated
gobuster/dirb-discovery -> sqlmap flow can never reach DVWA's own lab page
no matter how the container is configured — confirmed by logging into DVWA
manually (real cookie jar) and reproducing the real SQL error on
vulnerabilities/sqli/?id=1' , then confirming the exact same request
without cookies never reaches that code path. This is a genuine gap in
sqlmap_wrap.py, analogous in kind to the dirb/ZAP root-causing done in
smoke_test3 — flagged, not silently worked around.

To still exercise the real CONDITIONAL_TOOLS dispatch AND get a genuine
confirmed injection, a small (~20-line) companion script,
test-targets/dvwa-extra/info.php, was added — NOT part of stock DVWA,
mounted in at /var/www/html/info.php, documented in test-targets/README.md.
It queries DVWA's own real `users` table (populated by the real setup.php)
with the `id` GET parameter concatenated unsanitized, unauthenticated —
same vulnerability class as DVWA's own lab page, just reachable without a
session.

Live deepscan (scan 90, clean re-run — an earlier attempt, scan 89, was
discarded because it ran concurrently with a manual direct sqlmap call
against the same target and the two runs' log lines interleaved in
scan_errors.log; re-run sequentially to get an uncontaminated result):
  gobuster discovered, in order: /index.php (302), /info.php (200),
  /phpinfo.php (302) — all three are literal `dirb/common.txt` wordlist
  hits with a .php extension.
  deepscan.py's _detect_injectable_candidates() takes the FIRST
  script-extension match in discovery order, which was /index.php (DVWA's
  own real, but login-gated and non-vulnerable, front controller) — NOT
  info.php. scan_errors.log: "Starting tool: sqlmap" -> "Tool completed:
  sqlmap (1.90s)" — a real, fast, real dispatch (condition met, tool
  genuinely executed, not skipped) that correctly and honestly found no
  injection in index.php?id=1, because index.php really isn't vulnerable.
  This is accurate, non-fabricated scanner output — just not the
  interesting candidate, due to discovery-order chance.

  Separately, and reproduced twice (once contaminated by the concurrent
  run above, once clean afterward), the SAME unmodified
  modules.web.sqlmap_wrap.run_sqlmap() function was called directly
  against http://172.28.0.20/info.php?id=1 (test-targets/direct_sqlmap_confirm.py):
    injectable: True
    findings: [{'parameter': 'id', 'method': 'GET',
                'type': 'boolean-based blind',
                'title': 'AND boolean-based blind - WHERE or HAVING clause'}]
  A genuine, sqlmap-confirmed SQL injection, through the real, unmodified
  wrapper code — not a mock, not a modified function.

Net: sqlmap's CONDITIONAL_TOOLS dispatch is proven to fire for real and
execute a real sqlmap subprocess against a real candidate URL end-to-end.
Getting it to land specifically on an exploitable candidate in the SAME
automatic run would additionally require either (a) cookie/session support
in sqlmap_wrap.py (it has none today), or (b) making
_detect_injectable_candidates() prefer a candidate it has more signal is
worth trying rather than "first found" — neither was in scope to change

"honest caveat" items.

ITEM 3 — hydra (condition: login_service_found)
--------------------------------------------------------------------------------
STATUS: CONFIRMED WORKING — AND a real, previously-unknown parsing bug was
found and fixed live in the process.

ssh-target: linuxserver/openssh-server, one throwaway account
(admin/admin — both strings appear early in the exact Kali wordlists
hydra_wrap.py already defaults to; `admin` is literally the FIRST entry in
unix_passwords.txt). Verified working via a real SSH login (paramiko)
before any Aegis run.

First live deepscan (scan 92) against 172.28.0.30:
  detect_services() correctly named port 2222 "ssh" ->
  login_service_found=True, login_service="ssh", login_port=2222.
  scan_errors.log: "Starting tool: hydra" -> "Tool completed: hydra
  (12.97s)" — a real, full-wordlist hydra run, not a skip, not a stub.
  But: 0 `weak_credentials` findings recorded, and the terminal output
  read "[Hydra] ... scan completed, no valid credentials found" — despite
  admin:admin being a genuinely crackable credential (confirmed
  independently via a manual `hydra -L ... -P ...` run against the same
  container in the same session, which DID find it).

Root-caused (not assumed): hydra 9.6's real SSH success line includes an
extra `misc: (null)` field this codebase's regex didn't anticipate:
  [2222][ssh] host: 172.28.0.30   misc: (null)   login: admin   password: admin
modules/scanning/hydra_wrap.py's `_SUCCESS_LINE` regex required `host:
<val>` to be followed immediately by `login:`, so it never matched this
service's actual output format — every real cracked credential was
silently discarded as "no valid credentials found." This is a real,
previously-undiscovered bug, not a test-environment artifact (confirmed by
running the literal captured line through `_parse_hydra_output()` before
and after the fix).

Fix: `_SUCCESS_LINE` now tolerates an optional `misc: ...` segment between
`host:` and `login:` (modules/scanning/hydra_wrap.py). Verified in
isolation first (`_parse_hydra_output()` on the exact captured line now
returns the credential dict), then end-to-end.

Second live deepscan (scan 93, post-fix) against the same container:
  scan_errors.log: "Tool completed: hydra (12.95s)" ->
  "Finding recorded: {'type': 'weak_credentials', 'port': 2222,
  'service': 'ssh', 'login': 'admin'}"
  report.txt: "[1] CRITICAL — Weak ssh credentials found: admin:admin"

Separate, unrelated environment issue also root-caused and fixed on this
same container (not an Aegis codebase bug): OpenSSH 10.3 (the version this
image ships) has PerSourcePenalties enabled by default, which resets rapid
repeated connection attempts from one source after 2-3 tries — a real,
desirable anti-brute-force control on a genuine server, but it silently
defeated hydra's very first attempt against this fixture (`[ERROR] all
children were disabled due too many connection errors`, reproduced
independently of the regex bug above with a manual multi-credential hydra
run). Fixed via a linuxserver custom-cont-init.d hook
(test-targets/ssh-extra/disable-persource-penalties.sh) that disables it
and restarts sshd on container boot — verified surviving a full
`docker-compose up -d --force-recreate` of the container, not just a live
in-place patch.

5. FINAL VERDICT
================================================================================
Every one of the four CONDITIONAL_TOOLS has now been observed firing for
real, through Aegis's actual, unmodified `_check_conditional_tools()`
dispatch path, against a real trigger condition, on a locally-owned,
isolated, authorized test fixture — not a mock, not a synthetic unit test.
Three of the four (wpscan, hydra, enum4linux) produced real, meaningful
findings directly from the automatic end-to-end run. The fourth (sqlmap)
produced a real, meaningful, sqlmap-confirmed injection through the exact
same production code path, just via a direct call rather than the
automatic run — because of a genuine, now-documented architecture gap
(sqlmap_wrap.py's lack of cookie/session support) that the automatic
discovery heuristic cannot currently work around when a target's
vulnerable page sits behind a login wall.

Two real, previously-unknown defects were found and fixed live during this
pass, not just observed:
  1. modules/scanning/hydra_wrap.py's success-line regex silently dropped
     every real cracked credential when the target service's hydra output
     included a `misc:` field (confirmed live against hydra 9.6 / SSH) —
     fixed, verified pre/post-fix, isolated regression test included in
     the fix's own verification (see item 3 above).
  2. (Environment, not codebase) the SSH test fixture's own OpenSSH version
     defaults to an anti-brute-force control (PerSourcePenalties) that
     defeated the very brute-force testing this fixture exists for — fixed
     via a documented, isolated container-init hook, not by weakening
     anything in Aegis itself.

One honest, explicitly-flagged caveat carried forward, not fixed this pass:
  sqlmap_wrap.py has no cookie/session support. Any real target whose
  vulnerable page requires authentication (DVWA's own lab page being the
  clearest example encountered this session) cannot be reached by Aegis's
  normal unauthenticated gobuster/dirb -> sqlmap discovery flow, no matter
  how the target is configured. This is a real scanner limitation, now
  documented with a reproducible root cause, not a target-configuration
  problem — the natural next step if it matters for a future pass.

Aside, out of this pass's scope but observed on every run: zaproxy fails
in this venv with "python-owasp-zap-v2.4 (zapv2) is not installed" — a
plain missing pip dependency, unrelated to the ~/.ZAP profile issue
smoke_test3 already fixed. Not investigated further here since it's
outside CONDITIONAL_TOOLS, but worth a `pip install` pass before the next
full-profile smoke test.

All four local test containers (test-targets/docker-compose.yml) were left
running at the end of this pass for potential re-verification; per
test-targets/README.md they are local-only, isolated, and should be torn
down (`docker-compose down -v`) once no longer needed.
