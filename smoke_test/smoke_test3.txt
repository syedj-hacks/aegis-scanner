PART 2, item 8 — Issue E (dirb exit 255 against pentest-ground.com)
--------------------------------------------------------------------------------
STATUS: ROOT-CAUSED AND FIXED (root cause differs from every "likely
candidate" smoke_test2 guessed at — genuinely diagnosed this round, not
guessed).

Root cause (confirmed by direct live reproduction, twice): dirb is
single-threaded and opens one new connection per request. A full run
against pentest-ground.com with the default common.txt wordlist (4614
words) reliably dies with "(!) FATAL: Too many errors connecting to host
(Possible cause: RECV ERROR)" at almost exactly the same point both times
(1711/4612 words downloaded) — WITH and WITHOUT a 25ms -z flood-delay
between requests, which rules out a simple rate-based limiter (a delay
would have shifted the failure point in wall-clock time if it were purely
rate-based; it didn't) and points at a cumulative per-connection-count
threshold on the target/network side instead. gobuster (30 concurrent
threads, same wordlist, same target) never trips it because it finishes
long before reaching that many requests.

A second, independent bug compounded this: dirb writes its own abort
reason to STDOUT, not stderr, so dirb_wrap.py's failure branch (which only
checked stderr) fell through to run_tool()'s generic "non-zero exit code
(255)" and the real reason never reached scan_errors.log at all — this is
why smoke_test2 could only report the exit code, not a cause.

Fix (both parts):
  1. dirb_wrap.py's _DEFAULT_WORDLISTS now tries dirb's own bundled
     small.txt (959 words) first, falling back to common.txt and the
     others only if small.txt is missing. Verified live: small.txt against
     pentest-ground.com completed cleanly — exit 0, 959/959 words
     downloaded, no FATAL — where common.txt failed both times tested.
     gobuster is unaffected (still runs the full common.txt list; its
     speed is what let it avoid the threshold in the first place), so
     content-discovery coverage isn't reduced end-to-end, only dirb's own
     (supplementary, second-engine) slice of it.
  2. Added _extract_fatal_reason() to pull dirb's "(!) FATAL: ..." line out
     of stdout as a fallback when stderr is empty, so any future dirb
     failure (on this target or another) surfaces its real cause in
     scan_errors.log instead of a bare exit code.

Further confirmation from this session's full deepscan run against
scanme.nmap.org (a DIFFERENT target than the one the bug was root-caused
on): scan_errors.log shows dirb failing with "timed out after 300s" on
this exact target in TWO earlier historical runs (2026-07-24 23:32:50 and
2026-07-25 03:12:15-03:17:15, both before today's fix) — with today's
fix in place, the same target's dirb run completed cleanly in 246.15s
with 3 real discovered paths, no timeout, no FATAL. The fix generalises
beyond the one target it was diagnosed on.

PART 3, item 10 — ZAP baseline standalone
--------------------------------------------------------------------------------
STATUS: FIXED AND VERIFIED (environment fix, not a code change — zap_wrap.py
itself was never the problem).

Ran zap_wrap.run_zap_baseline() standalone against scanme.nmap.org AND
pentest-ground.com. Both completed cleanly end-to-end (daemon starts,
spider genuinely crawls the site) but returned 0 alerts on both targets.
This looked like a real bug, so it was investigated to a definitive root
cause rather than accepted at face value, and — on being asked directly
whether it was actually fixed — pursued to a full fix rather than left as
"root-caused only":

  zap.pscan.scanners listed only 3 trivial active rules (WSDL File
  Detection, Script Passive Scan Rules, Stats Passive Scan Rule). The real
  vulnerability-detection ruleset add-on ("Passive scanner rules",
  id=pscanrules, ~60 rules — missing headers, CSP, cookie flags, info
  disclosure, vulnerable-JS-library detection, etc.) was not active.

  Three in-daemon install attempts (marketplace-by-id, the API's
  install_local_addon action, the installScannerRules config flag) each
  failed for a distinct, confirmed reason — see the root-cause chain
  below. Grepping ZAP's own zap.log for history turned up the real
  explanation: pscanrules v70.0.0 WAS successfully installed and loaded at
  02:32:51 earlier the same day (visible in an "Installed add-ons: [...]"
  log line from a session that predates this one), then silently vanished
  from every subsequent "Installed add-ons" list with no error ever logged
  against it specifically — while roughly a dozen OTHER add-ons visibly
  updated to newer versions in that same window. This is consistent with
  an add-on auto-update reconciliation (most likely triggered by this
  session's own earlier `-addonupdate` diagnostic call) that uninstalled
  the old pscanrules version as part of updating everything else, then
  failed to install the replacement because the marketplace catalog
  lookup for that specific id was failing (the same "Failed to find
  Add-on: pscanrules" error seen throughout this diagnosis) — leaving it
  permanently uninstalled rather than restored.

  The actual fix: ZAP's `~/.ZAP` profile directory is pure local
  cache/state, not something zap_wrap.py or any other part of this
  codebase depends on persisting. A completely fresh `~/.ZAP` (full
  backup taken first) forces ZAP's own local-plugin-directory bootstrap to
  re-run from scratch — confirmed live: a from-nothing daemon start
  detected "31 newer addons," downloaded them for real over the network
  (confirmed via active outbound connections while it ran — NOT killed
  mid-download, since that's the exact corruption mode zap_wrap.py's own
  design docs already warn about), and came up with 61 real passive-scan
  rules loaded. A clean shutdown via the API (`zap.core.shutdown()`, the
  same call zap_wrap.py's own `finally` block already makes) persisted
  that state to `add-ons-state.xml` for the first time. A second, fully
  independent daemon start afterward loaded all 61 rules again with zero
  re-bootstrap or network activity, confirming the fix survives a restart
  — it isn't a one-off in-memory fluke.

  End-to-end confirmation through the real zap_wrap.py code path (not a
  diagnostic script):
    pentest-ground.com: 1 real alert — "Server Leaks Version Information
      via 'Server' HTTP Response Header Field" (rule 10036)
    scanme.nmap.org: 7 real alerts, including "Missing Anti-clickjacking
      Header" (MEDIUM), "Content Security Policy (CSP) Header Not Set"
      (MEDIUM), "Sub Resource Integrity Attribute Missing" (MEDIUM), and
      4 INFO-level findings

Severity: was a real, user-visible gap (ZAP contributed zero evidence to
any report); now closed. No code in zap_wrap.py or elsewhere changed —
this was entirely an environment/state fix. Flagged for whoever
next touches this machine's ZAP install: avoid running `-addonupdate` or
marketplace-based `-addoninstall` against this profile casually, since
that specific action sequence is the leading suspect for how pscanrules
got silently uninstalled in the first place.

PART 3, item 12 — real-TTY skip-key test
--------------------------------------------------------------------------------
STATUS: FIXED AND VERIFIED against a REAL tool in a REAL scan (not the
synthetic sleep-based pty test smoke_test2 used) — AND a genuine,
previously-undiscovered bug was found and fixed in the process.

Method: a real pseudo-TTY (Python's pty.openpty(), not a mock) drove
`python3 aegis.py pentest-ground.com --profile quickscan -v` end-to-end. A
background thread tailed scan_errors.log (plain text, no ANSI/Live-render
interleaving — the first attempt tried to pattern-match Rich's
progress-bar-decorated console stream directly and that approach silently
never matched anything, because Rich's Live-progress redraw sequences
fragment adjacent print() calls in the raw byte stream; switching to the
plain log file fixed the test harness itself) and pressed the real skip
key ('s') the moment it saw "Starting tool: nmap" (compulsory — expect
refusal) and again at "Starting tool: nuclei" (skippable — expect it to
actually stop).

Results (two independent runs, same behaviour both times):
  (a) nmap (compulsory): skip key sent at t=1.2-1.4s into a ~3.2s natural
      run. Console output captured the real refusal message: "[!] cannot
      be skipped — every downstream module (service detection, web audit,
      CVE lookup, conditional tools) depends on its open-port list.
      Ignoring skip request." nmap's logged duration (3.18-3.20s) matched
      its normal unskipped completion time both times — not cut short.
  (b) nuclei (skippable): skip key sent as soon as "Starting tool: nuclei"
      appeared. scan_errors.log recorded "Tool skipped by user: nuclei"
      (WARNING level) and the scan moved on to reporting immediately.

  Bug found and fixed during this test: the FIRST run's final stats showed
  {'tools_run': 5, 'tools_failed': 1, 'tools_skipped': 0} — the skip was
  executed and logged correctly, but every one of the 15 tool-wrapper
  modules (nuclei_wrap.py, nikto_wrap.py, gobuster_wrap.py, dirb_wrap.py,
  whatweb_wrap.py, sslyze_wrap.py, sqlmap_wrap.py, wpscan_wrap.py,
  hydra_wrap.py, enum4linux_wrap.py, service_detect.py, port_scanner.py,
  dns.py, osint.py, subdomain.py) dropped run_tool()'s `skipped` flag when
  building its own return dict, so every profile orchestrator's stats
  computation (`tools_failed = error and not skipped`) miscounted every
  skip as a failure instead. This affected the SCAN SUMMARY panel's
  accuracy for every profile, on every skippable tool, since the skip
  keybind feature was introduced — not caught by smoke_test2's synthetic
  pty test because that test used bare "sleep" commands directly through
  run_tool(), never through a real wrapper module, so it could never have
  seen this gap. Fixed by propagating `result["skipped"] =
  tool_result.get("skipped", False)` in all 15 wrappers (plus zap_wrap.py
  and subdomain.py's aggregate case, for contract consistency even though
  neither can currently trigger it the same way). Re-ran the identical
  live pty test after the fix: stats correctly showed {'tools_run': 5,
  'tools_failed': 0, 'tools_skipped': 1}.

PART 3, item 13 — DB write concurrency sanity check
--------------------------------------------------------------------------------
STATUS: VERIFIED SAFE, no code change needed.

database/db.py's insert_scan()/insert_finding()/insert_findings_bulk() all
call get_connection() fresh (a real sqlite3.connect() per call, not a
shared module-level/global connection), commit, and close within the same
function call — there is no shared connection object anywhere in the
file. Python's sqlite3 module's default busy-timeout (5s) gives concurrent
writers room to serialise through SQLite's own file locking rather than
immediately raising "database is locked".

Incidental live evidence from this session's own tooling accident (item
11's scan 79, killed mid-run by an external timeout): the `scans` table
row was inserted and committed, but zero `findings` rows exist for that
scan_id — exactly the state you'd want from a clean per-call-commit
design (no partial/torn finding rows, no corruption of scan 77/78/80's
data despite the interruption happening in the same database file within
the same few minutes as three other completing runs).
