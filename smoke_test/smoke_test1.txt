Known Issue #5 — Severity/finding-count distribution inconsistent with profile
depth (stealthscan showing fewer/zero findings than quickscan)
--------------------------------------------------------------------------------
Verdict: CONFIRMED — root cause fully identified, 100% reproduction rate (3/3
targets).

Symptom: stealthscan produced exactly 0 findings against every single target,
including pentest-ground.com, which quickscan's much shallower -F scan found real
open ports on 36 seconds earlier in the very same sweep:
  scanme.nmap.org__stealthscan.meta:      duration_s=301  finding_count=0
  testphp.vulnweb.com__stealthscan.meta:  duration_s=300  finding_count=0
  pentest-ground.com__stealthscan.meta:   duration_s=300  finding_count=0
scan_errors.log (all three targets), verbatim:
  "Tool failed: nmap — timed out after 300s"

Root cause: modules/utils/config.py defines PROFILES['stealthscan']['nmap_args']
= ['-T1', '-p-', '--randomize-hosts', '-Pn'] — a full 65535-port sweep at nmap's
slowest ("Sneaky") timing template — but TOOL_TIMEOUTS['nmap'] is hardcoded to
300 seconds, the same budget quickscan's -F (~100-port) scan uses. -T1 alone
makes a full-port sweep take far longer than 300s regardless of target
responsiveness (confirmed: it hit exactly the 300s wall on all 3 targets, 2 of
which are fast/clean responders). modules/utils/error_handler.py:run_tool()
kills the process via subprocess.communicate(timeout=...) at 300s and sets
success=False (lines 128-134); modules/scanning/port_scanner.py:scan_ports()
then short-circuits on any tool_result failure (lines 196-201) and returns
open_ports=[] wholesale — none of the ports nmap had already found before being
killed are recovered, because the killed process's XML output is either
incomplete/unparseable or simply never reaches _parse_nmap_xml().

Why it's happening: a single hardcoded per-tool timeout (config.py
TOOL_TIMEOUTS['nmap']=300) is applied uniformly regardless of how heavy the
profile-specific nmap_args actually are, combined with an all-or-nothing result
contract in scan_ports() that discards 100% of partial results on any failure.

Recommended fix: (a) give nmap a timeout that scales with its actual args — e.g.
a separate, much larger TOOL_TIMEOUTS entry for -p- profiles, or compute a
timeout dynamically in port_scanner.py/scan_ports() based on whether '-p-' or a
slow -T value is present in nmap_args; and (b) make scan_ports() attempt to
parse whatever XML nmap had written before being killed (nmap can be pointed at
a real output file and re-read after a SIGTERM, or SIGTERM instead of SIGKILL
can be tried first to let nmap flush a valid partial <nmaprun> document) instead
of discarding everything on timeout.

Severity: BLOCKS USAGE — stealthscan's entire reason to exist (a full port
sweep) is non-functional against any real target today.

Known Issue #1 — No way to skip/interrupt a single hung tool; does a slow tool
block the whole profile?
--------------------------------------------------------------------------------
Verdict: REFINED / PARTIALLY CONFIRMED.

Symptom: No single tool can hang forever — every modules/*/*_wrap.py call goes
through error_handler.run_tool(), which enforces config.TOOL_TIMEOUTS per tool
via subprocess.communicate(timeout=...) and unconditionally kills the process on
expiry (error_handler.py:128-134). That part of the concern is NOT reproduced:
nikto, gobuster, dirb etc. all self-terminated on schedule in every run.
However, there is no AGGREGATE wall-clock budget across the tools x ports a
profile runs, and this sweep's own external 900s cap had to kill 2 of 15 runs
because of it:
  "=== END pentest-ground.com__webaudit ... duration=900s exit=124 timed_out=yes ==="
  "=== END pentest-ground.com__deepscan ... duration=900s exit=124 timed_out=yes ==="
webaudit against pentest-ground.com (3 open web-ish ports: 80, 81, 443) had
finished ports 80 and 81 and was midway through nikto on port 443 when killed —
i.e. each individual tool honoured its own timeout, but headers+nikto(600s)+
gobuster(300s)+dirb(300s)+whatweb(60s)+sslyze(60s), repeated per port, has no
ceiling and legitimately summed past 15 minutes.

Root cause: modules/profiles/webaudit.py and deepscan.py's per-port for-loops
(webaudit.py:217-250, deepscan.py:505-544) have no time budget of their own —
each iteration just calls the next tool unconditionally regardless of how much
wall-clock the port loop has already consumed.

Why it's happening: TOOL_TIMEOUTS bounds a single subprocess call, not a
profile run; nothing multiplies that bound by "number of ports this profile
found" to produce a realistic profile-level expectation.

Recommended fix: track elapsed time inside the per-port loop in webaudit.py /
deepscan.py and stop starting new tools (log + skip remaining ports/tools)
once a configurable profile-level budget is exhausted, so a target with many
open web ports degrades to a partial-but-real result instead of an unbounded
run time.

Severity: degrades usability heavily at scale — for any time-boxed use (CI, a
scheduled scan window) a target with 2-3 open web ports can make webaudit or
deepscan run far longer than expected, and (see Issue D below) actually lose
data if something does eventually kill it.

Known Issue #6 — banner.py timing out on both 80 and 443 in deepscan
--------------------------------------------------------------------------------
Verdict: CONFIRMED as described, but the underlying behaviour is intentional
per the module's own docs — the real defect is elsewhere (log severity/wasted
time).

Symptom, reproduced verbatim on pentest-ground.com's deepscan run, immediately
after nmap-sV had already correctly identified nginx 1.31.3 on both ports:
  "Tool failed: banner_grab:80 — timed out"
  "Tool failed: banner_grab:443 — timed out"
~24 seconds elapsed between "Starting tool: banner_grab" (00:22:12) and "Tool
completed: banner_grab" (00:22:36) for just these two ports.

Root cause: modules/scanning/banner.py:_grab_single() opens a raw socket and
blocks on recv() with a 5s timeout, then retries once (another 5s + 1.5s pause)
before giving up — a combined ~11.5s "timeout" per port. HTTP(S) servers don't
send an unsolicited banner (they wait for a request first), so this always
times out on ports 80/443/8080/8443 by construction — banner.py's own comments
say as much ("Request-driven services (HTTP) simply time out here and yield an
empty banner — that's fine, -sV covers them"). In this run, -sV genuinely had
already captured the same information via a different code path (an actual
HTTP request), so no data was lost.

Why it's happening: banner.py probes every open port unconditionally, with no
awareness of which ports scan_ports()/detect_services() already identified as
HTTP(S) (where a raw-socket banner grab is known to be pointless).

Recommended fix: skip ports already known to be HTTP/HTTPS (deepscan.py already
computes _is_web_port() for this exact purpose — reuse it to filter the port
list passed to grab_banners()), or at minimum log this specific outcome at
INFO/DEBUG rather than ERROR so scan_errors.log doesn't read as if two real
failures occurred.

Severity: cosmetic / minor efficiency — no data loss, but ~24s wasted per
deepscan run with 2 HTTP(S) ports open, and misleading ERROR-level log noise.

NEW Issue A — Duplicate logging across virtually every tool wrapper (systemic)
--------------------------------------------------------------------------------
Symptom: every "Starting tool: X" / "Tool completed: X" / "Tool failed: X" line
in scan_errors.log appears exactly twice, in every one of the 15 runs, e.g.
(testphp.vulnweb.com deepscan, verbatim):
  "2026-07-24 23:49:03 [INFO] ... Starting tool: subfinder"
  "2026-07-24 23:49:03 [INFO] ... Starting tool: subfinder"
  "2026-07-24 23:49:22 [INFO] ... Tool completed: subfinder (19.29s)"
  "2026-07-24 23:49:22 [INFO] ... Tool completed: subfinder (19.29s)"
Also reproduced for nmap, amass, theHarvester, nikto, gobuster, dirb, whatweb,
sslyze, header_check, and every nmap timeout/failure message across all 15
runs — this is a codebase-wide pattern, not a one-off.

Root cause: modules/utils/error_handler.py:run_tool() already calls
log_tool_start()/log_tool_success()/log_tool_failure() internally (lines 85,
118, 121, 134) as part of its documented contract. But essentially every
wrapper module that calls run_tool() — modules/recon/dns.py, subdomain.py,
osint.py, modules/scanning/port_scanner.py, service_detect.py, and every
module under modules/web/ (nikto_wrap.py, gobuster_wrap.py, dirb_wrap.py,
whatweb_wrap.py, sslyze_wrap.py, zap_wrap.py, nuclei_wrap.py, wpscan_wrap.py,
sqlmap_wrap.py) and modules/scanning/hydra_wrap.py, enum4linux_wrap.py — ALSO
calls log_tool_start()/log_tool_success()/log_tool_failure() itself,
independently and redundantly. The one correct exception is
modules/scanning/banner.py, which does NOT go through run_tool() (raw sockets
via safe_call(), which does not log start/success itself) — its explicit
log_tool_start() call there is necessary and is the one place this pattern is
NOT a bug.

Why it's happening: a systemic copy-paste/legacy pattern — every wrapper was
apparently written assuming it owned its own logging, and this was never
reconciled after run_tool() itself grew the same logging as a first-class part
of its contract.

Recommended fix: remove the explicit log_tool_start/log_tool_success/
log_tool_failure calls from every wrapper module listed above (leave run_tool's
internal ones as the single source of truth); leave banner.py's calls alone.

Severity: degrades data quality — doubles scan_errors.log volume across every
single scan this tool ever runs, and makes debugging via logs noisier/more
confusing (e.g. a single nmap timeout reads as two separate failure lines).

NEW Issue B — compliance's ssl-enum-ciphers script often fails to run against
the actual HTTPS port because nmap_args has no explicit port scope
--------------------------------------------------------------------------------
Symptom: in the live sweep, neither compliance run (scanme.nmap.org scan 47,
pentest-ground.com scan 57) persisted an ssl-enum-ciphers finding for ANY port,
despite pentest-ground.com definitely serving TLS on 443 (confirmed
independently — see below). compliance.py's own fallback logic quietly papered
over the gap by running sslyze against port 443 anyway (via its
_FALLBACK_TLS_PORT path), so the TLS audit wasn't a total loss, but the
profile's headline nmap-script cipher finding — which compliance.py's own
docstring calls "the highest-priority gap in the whole codebase" — was
silently absent both times, with no error logged.

Root cause, confirmed by direct reproduction outside aegis-scanner: running the
exact command compliance.py builds (`nmap -T4 --script
ssl-enum-ciphers,http-headers -oX - pentest-ground.com`, no -p flag) three
times in a row against the same live target produced three DIFFERENT outcomes:
run 1 — ssl-enum-ciphers ran on NO port at all; run 2 — it ran on port 81 (an
obscure secondary TLS listener) but NOT on port 443; only when explicitly
scoped with `-p 443` did it reliably run against port 443 and return real
cipher data every time. modules/utils/config.py's PROFILES['compliance']
['nmap_args'] has no `-p` restriction (unlike webaudit's, which is scoped to
`-p 80,443,8080,8443`), so nmap scans its default ~1000-port list and lets
NSE's own portrule/service-detection heuristics opportunistically decide which
of several plausible ports to run the SSL script against — a choice this
sweep's evidence shows is not reliable.

Why it's happening: without -sV and without explicit port scoping, nmap's
script engine has to guess which open ports are "SSL-like" using only a
table-based service-name guess plus its own script scheduling heuristics, and
that guess is demonstrably inconsistent between runs against the very same
target.

Recommended fix: scope compliance's nmap_args to explicit candidate ports the
same way webaudit already does (e.g. `-p 80,443,8443` ahead of `--script ...`
in config.py), or — mirroring the two-stage pattern service_detect.py already
uses for -sV — run scan_ports() first to learn open_ports, then issue a second,
explicitly `-p <tls candidate ports>`-scoped `--script ssl-enum-ciphers` pass.

Severity: degrades data quality — a silent, non-obvious gap in the compliance
profile's core deliverable (no error is logged when it happens, so nobody
would notice without diffing nmap's raw XML the way this investigation did).

NEW Issue C — Product name silently dropped from persisted/reported findings
(quickscan/stealthscan-shaped raw service rows)
--------------------------------------------------------------------------------
Symptom: nmap -sV correctly identifies both product and version and prints
them correctly to the console:
  "[+] [Services] pentest-ground.com:80 -> http (nginx 1.31.3)"
but the persisted finding and the resulting report only ever say:
  "1. [LOW     ] port 80 — http 1.31.3"
"nginx" — the actual, most security-relevant piece of information nmap
found — never appears anywhere in the database or the report for this profile.
Confirmed in both scanme.nmap.org (Apache httpd 2.4.7 -> reported as merely
"http") and pentest-ground.com (nginx 1.31.3 -> reported as merely "http")
quickscan runs.

Root cause: database/db.py's `findings` table schema has columns port,
service, version, cve_id, cvss, severity, description, remediation,
finding_type — there is no `product` column. modules/scanning/
service_detect.py:_parse_sv_xml() correctly returns {port, service, version,
product} per port, but modules/profiles/quickscan.py:134-144 passes that raw
dict list straight into insert_findings_bulk() unmodified; database/db.py:
insert_finding() only ever reads finding.get("service")/finding.get("version")
(lines ~101-103), so "product" is silently dropped on the way into SQLite.
(deepscan.py does not have this problem for its CVE-enriched findings, because
_enrich_services() builds an explicit description string containing the
product before those rows are ever inserted — but quickscan's raw,
unenriched-by-design service rows go in as-is.)

Why it's happening: a schema/mapping gap — the "findings" table was designed
around CVE-shaped rows, and the raw-service-row code path was never updated to
either add a product column or fold product into an existing text field before
insertion.

Recommended fix: either add a `product` column to the findings table (schema
already has a documented history of not perfectly fitting every finding shape)
and have insert_finding() persist it, or, with less schema churn, have
quickscan.py build a description string that includes the product (the same
way deepscan.py's _enrich_services() already does via `" ".join(x for x in
(product, version) if x)`) before calling insert_findings_bulk().

Severity: degrades data quality — an analyst reading a quickscan/stealthscan
report has no idea whether a service is nginx, Apache, or IIS without
re-running a deeper scan, which defeats much of the point of a "quick" pass.

NEW Issue D — Interrupted profile runs lose 100% of their findings, not just
the interrupted tool's
--------------------------------------------------------------------------------
Symptom: reproduced twice in this sweep, on the two runs killed by this test's
900s external cap. pentest-ground.com's webaudit run logged 22 real,
individually-recorded findings to scan_errors.log as DEBUG "Finding recorded:
{...}" lines (nikto hits on port 80, six missing-security-header findings plus
a Server fingerprint on port 443) before being killed mid-way through nikto on
port 443 — yet the database shows finding_count=0 for that scan (scan_id=55),
and no report.txt/report.pdf reflects any of that work. The deepscan run
against the same target shows the identical pattern: 41 findings logged,
finding_count=0 persisted, no report.pdf generated at all (confirmed via
`ls output/pentest-ground.com/report.pdf` — file does not exist for this run,
unlike the two deepscan runs that completed normally and each produced a
~14KB PDF).

Root cause: modules/profiles/webaudit.py (and deepscan.py, compliance.py,
quickscan.py, stealth.py — the same pattern repeats in every profile
orchestrator) accumulates findings in a plain Python list across the entire
function body and calls insert_findings_bulk(scan_id, findings) exactly ONCE,
at the very end (webaudit.py:280), after every port's full tool loop has
already finished. Nothing is written to the findings table incrementally.

Why it's happening: log_finding() (called by every tool wrapper as it goes)
durably writes to scan_errors.log immediately, but that is a text log, not the
structured findings table the report writers actually read from
(modules/reporting/summary.py -> build_summary() only ever queries the
database) — so a kill at any point before the final bulk insert throws away
everything that was only ever sitting in an in-memory list.

Recommended fix: call insert_findings_bulk() (or per-finding insert_finding())
incrementally — e.g. once per port, right after that port's tool loop finishes,
rather than batching the entire profile's findings into one list held for the
whole run. This also naturally bounds how much work a kill at any point can
lose to "the current port," rather than "the entire scan."

Severity: BLOCKS USAGE / the most severe finding-quality issue in this report.
Combined with Issue #1/A's lack of an aggregate time budget, any moderately-
scoped webaudit or deepscan run against a real multi-port target is likely to
eventually get killed by something (a CI timeout, an operator's Ctrl+C, an
OOM), and when it does, the operator is left with a completely empty report
despite the tool having genuinely done — and logged — real, useful work.

Symptom: scanme.nmap.org's webaudit run (scan_id=45) persisted a CRITICAL,
CVSS 9.8 finding for CVE-2016-6814 against port 80's "Apache/2.4.7" web
server:
  {'cve_id': 'CVE-2016-6814', 'cvss': 9.8, 'severity': 'CRITICAL',
   'description': '...Codehaus versions of Groovy...Apache Groovy 2.4.4 to
   2.4.7 on classpath...it was possible for an attacker to bake a special
   serialized object that will execute code directly when deserialized...'}
CVE-2016-6814 is a Java deserialization RCE in Apache Groovy (a JVM scripting
language) — completely unrelated to the Apache HTTP Server (httpd) binary
nmap actually detected. This is a false positive that would send an analyst
down a real dead end chasing a Groovy classpath vulnerability on a machine that
almost certainly has no Groovy installed at all.

Root cause: modules/enrichment/cve_lookup.py:_build_keyword() (line 126-134)
joins product+version into a bare space-separated string ("Apache 2.4.7") and
sends it to NVD's keywordSearch, which — per the module's own docstring — is a
plain AND-of-words match with no product/CPE disambiguation. "Apache" is the
name of a software foundation that owns dozens of unrelated projects (httpd,
Groovy, Tomcat, Struts, ...), so any CVE whose free-text description happens
to contain both "Apache" and "2.4.7" matches, regardless of which actual
project it concerns.

Recommended fix: qualify the query with a more specific product token before
sending it to NVD (e.g. map nmap's generic "Apache" product string to "apache
httpd" the way _parse_banner() already normalises Server-header product
names), or post-filter NVD results by checking the returned CVE's CPE match
strings actually reference the httpd product rather than trusting a bare
keyword hit.

Severity: degrades data quality significantly — a false CRITICAL/9.8 is
exactly the kind of result that erodes trust in every other finding the tool
produces.

NEW Issue F — Naive substring keyword matching in severity.py inflates a
routine nikto finding to CRITICAL
--------------------------------------------------------------------------------
Symptom: the same scanme.nmap.org webaudit run (scan_id=45) graded this nikto
finding as CRITICAL:
  "[999965] /index: Apache mod_negotiation is enabled with MultiViews, which
  allows attackers to easily brute force file names. The following
  alternatives for 'index' were found: index.html."
This is a routine, low-impact information-disclosure finding (nikto itself
does not flag it as especially severe) — it should never be CRITICAL.

Root cause: modules/enrichment/severity.py:_NIKTO_KEYWORDS's CRITICAL tier
(line ~182) includes the bare abbreviation "rce" (intended to mean "remote
code execution"), and _match_keywords() (line ~289) does plain substring
containment — `if keyword in lowered` — with no word-boundary check. The
phrase "brute force" contains the literal substring "...fo-RCE...", so it
coincidentally matches the CRITICAL "rce" keyword. Reproduced deterministically
in isolation:
  >>> score_finding({'type': 'nikto_finding', 'description': "...brute force
      file names...", 'reference': ''})
  {'severity': 'CRITICAL', 'severity_source': 'heuristic', ...}

Recommended fix: switch _match_keywords() to word-boundary regex matching
(`\bkeyword\b`) instead of plain `in` substring containment, and/or drop
short, collision-prone abbreviations like "rce" from the keyword lists in
favour of less ambiguous phrases (e.g. "remote code exec").

Severity: degrades data quality — directly corrupts severity distribution
(the same underlying category of concern as known issue #5, but at the
per-finding rather than per-profile level) and produces alarming false-CRITICAL
noise identical in effect to Issue E.

NEW Issue G — testphp.vulnweb.com unreachable from this test environment
(environmental, not a code bug)

Symptom: all 5 profiles against testphp.vulnweb.com returned 0 open ports / 0
findings, each completing in 3-5 seconds (quickscan/webaudit/compliance) —
only stealthscan/deepscan took longer, and only because they still had to
spend their own internal recon/nmap timeout budgets before concluding the same
thing.

Confirmed independently, outside aegis-scanner: `curl -sI --max-time 10
http://testphp.vulnweb.com/` returned nothing at all, and raw TCP connects to
both port 80 and port 443 timed out after 5s. As a control, the identical
probes against scanme.nmap.org:80 and pentest-ground.com:80/443 both succeeded
immediately. This means testphp.vulnweb.com is not reachable on any web port
from this specific network/environment for the duration of this test — nmap
and aegis-scanner both behaved correctly given what the network actually
returned ("nmap completed but found no open ports" is the true state).

Not a code bug. Flagged here purely so these 5 runs are not misread as
"webaudit/deepscan found nothing on a known-vulnerable test app," which would
be the wrong conclusion — this target's results in this report validate only
the "target has zero open ports" code path, not real web-application scanning.

Additional minor/cosmetic observation (not a full issue write-up)
--------------------------------------------------------------------------------
Every SCAN SUMMARY panel prints "Tools run: 0 | Tools failed: 0" regardless of
how many tools actually ran or failed (confirmed in every one of the 15 runs'
stdout). This is intentional and documented — modules/reporting/summary.py:
summary_stats() explicitly hardcodes both to 0 with a comment explaining "which
tools ran is not persisted in the scans table, and inventing a number would
misreport the scan" — but the two numbers are visually indistinguishable from
a real (and wrong) "0 tools ran" result, which could read as a scan-level
failure to someone glancing at the summary. Consider either omitting the line
entirely when the data isn't tracked, or persisting real tool-run/tool-failed
counts (each profile orchestrator already computes them locally via `stats =
{"tools_run": len(tool_results), ...}` and passes them to log_scan_end() —
that same data just never reaches the summary panel).
