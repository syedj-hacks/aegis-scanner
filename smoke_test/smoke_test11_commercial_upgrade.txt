 PER-ITEM STATUS
--------------------------------------------------------------------------------

1. --help + Ctrl+C ...................... DONE, verified (PTY probes)
   The reported "Ctrl+C skips the tool" text was wrong on TWO counts:
   - the panel promised unconditional skip; Ctrl+C only skips WHILE a tool is
     running (run_tool/safe_call intercept it). In the gaps between tools it
     propagates to main() and ends the scan. Measured live: SIGINT during a
     subprocess -> clean skip, scan continues; SIGINT between tools -> exit.
     Panel + COMMANDS.txt + TUTORIAL all corrected; the skip key is now
     presented first as the reliable control.
   - run_tool()'s KeyboardInterrupt branch set error but never skipped=True, so
     a deliberate Ctrl+C skip was classified a TOOL FAILURE. Fixed + re-probed.
   --help rewritten beginner-first, profile table generated live from PROFILES.

2a. Parallel per-port web tools ......... DONE, verified LOSSLESS
    nikto/gobuster/dirb/whatweb/sslyze pooled per port, order-preserving.
    Prerequisite fixes: the skip-key listener (was per-call termios save/restore
    -> refcounted singleton) and get_logger() (was racy -> lock-guarded).
    PARITY PROVEN: DVWA deepscan sequential(198) vs concurrent(201) = 48 vs 48
    findings, identical severity split, diff = 0 new / 0 fixed / 48 unchanged.

2b. Parallel nmap chunk sweep ........... DONE, verified (wave scheduling)
    MAX_CONCURRENT_NMAP_CHUNKS=3, runs in waves to keep stop-on-first-failure;
    merges in port-range order. Sequential path proven byte-identical by a
    fake-nmap harness.

    >>> TIMING — read this carefully, the number is not a simple win <<<
    Two A/B runs were done (concurrency OFF vs ON, same code, back to back):

      Run 1, scanme.nmap.org : 1530.7s -> 510.2s  (3.00x)   *** DISCARDED ***
        Thrown out: the host degraded between the two halves (it stopped
        answering entirely — confirmed with a live probe afterwards). The
        "after" run lost 16 findings, ALL from the sequential tools (ZAP 7,
        nmap_script 4, nuclei 2, service_version 2, nikto 1) and NONE from the
        parallelised ones. So that 3.00x measured target decay as much as
        concurrency, and is not trustworthy.

      Run 2, DVWA container  :  536.9s -> 568.2s  (0.94x)   *** CLEAN ***
        Uncontaminated (localhost, stable throughout, 48=48 findings both ways)
        and shows essentially NO speedup — 5.8% SLOWER, within noise.

    The honest conclusion is that the speedup is ENTIRELY target-latency
    dependent, and that is the correct mechanism, not a disappointment: the pool
    overlaps network WAIT. A localhost target has almost none to overlap, so the
    thread/pool overhead slightly dominates; a slow/filtered remote host (where
    each tool spends most of its time waiting on the wire) is where overlapping
    those waits pays off. We do NOT have a clean measurement of that remote case
    — the one target that would have shown it is the one that degraded. So:

      * concurrency is proven CORRECT (lossless) on a real deepscan,
      * concurrency is proven to add no overhead worth worrying about on a fast
        target,
      * the size of the win on a slow remote target is UNMEASURED. Claiming
        "3x faster" would be dishonest.

--------------------------------------------------------------------------------
 BUGS FOUND AND FIXED DURING VERIFICATION  (the important part)
--------------------------------------------------------------------------------

These were NOT in the plan. They were found by actually running the thing, and
three of the four are the same shape as this project's signature failure mode: a
tool that could not reach its target reporting a clean-looking "nothing found".

#1  diff phantom churn (found: item 8 live run)
    --diff 137 168 reported 1 new + 1 fixed for ONE nikto finding whose allowed-
    methods list came back in a different order ("OPTIONS, GET, ..." vs "GET,
    ..., OPTIONS"). The description-fallback key didn't normalise set ordering.
    Fixed: _normalise_enumeration() sorts a trailing enumeration; prose with a
    comma is left alone. Re-diff: 0 churn. 29 assertions pin it.

#2  testssl invisible failure (found: item 3 live run)   [same class as scan 97]
    badssl.com began refusing connections mid-verification. testssl.sh exits
    non-zero AND writes a valid JSON file containing {scanProblem, FATAL}. The
    wrapper salvages non-zero exits on purpose (testssl exits non-zero when it
    FINDS things), so it salvaged this too -> "scan completed, no TLS issue
    found" about a host it never reached. Reproduced deterministically (closed
    port, exit 246, 766 bytes valid JSON, 0 findings, reported success). Fixed:
    scanProblem/FATAL is now a tool FAILURE. 18 assertions pin it.

#3  ZAP invisible failure (found: item 9 live run)       [same class as scan 97]
    The container could not route to the DVWA lab's Docker network. ZAP reported
    a complete 100% spider and zero alerts — byte-identical to "target is clean".
    This matters MORE now that ZAP_HOST exists: a remote daemon has its own
    routing, so "the scanner can reach it" no longer implies "ZAP can". Fixed:
    the wrapper checks ZAP's own site tree (core.urls), not the spider's
    attempted-URL list (which is non-empty even on total failure), and reports a
    reachable-nothing scan as a FAILURE. Verified both ways: unreachable ->
    failed; example.com through the same container -> 4 alerts, ran.

#4  deepscan sqlmap NameError (found: item 2b A/B run)
    run_sqlmap(..., auth=auth) was added inside _check_conditional_tools(), which
    had no `auth` parameter. A NameError that only fires when a target's content
    produces an injectable candidate — which the finding-sparse smoke targets
    never did, so the checkpoint commit shipped it. Caught the moment a deepscan
    ran against injectable DVWA. Fixed: auth threaded through. Now verified live
    firing — 2 CRITICAL SQLi findings across the two DVWA A/B runs, sqlmap
    outcome=ran.

    (#4 also incidentally fixed the field-signature inconsistency #4b: summary.py
    declared sslyze_finding/missing_security_header CVSS-inapplicable, which item
    6 makes false. _NOT_APPLICABLE["cvss"] and cvss_display() updated; the
    attribution audit flagged it the day the engine landed, which is the check
    doing its job.)

--------------------------------------------------------------------------------
 WHAT WAS NOT DONE / COULD NOT BE VERIFIED LIVE  (honesty)
--------------------------------------------------------------------------------

- The remote-target deepscan speedup is UNMEASURED (see item 2b). We have "no
  loss" and "no overhead on localhost"; we do NOT have a trustworthy remote
  speedup figure, because the target that would show it degraded mid-test.

- testssl live runs used a scratch git clone, not the apt package, because apt
  needs sudo unavailable in this environment. The wrapper's binary resolution
  and JSON parsing are identical either way, and the install.sh apt+fallback
  path is code-reviewed but was not executed on a clean machine here.

- The ZAP container was verified against example.com and (negatively) the local
  lab. It was not run against the lab POSITIVELY, because that needs the compose
  network wiring documented in docker-compose.yml — which is documented but not
  applied to the running container in this pass.

- stealthscan was verified by its regression guard (15 assertions) and a live
  96.9s run, not by a full findings comparison — by design, it produces only
  open-port findings and the guard covers its config exactly.
