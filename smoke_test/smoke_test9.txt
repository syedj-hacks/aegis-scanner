2.2 The two call sites
--------------------------------------------------------------------------------
Both are in modules/profiles/deepscan.py and both are correct in isolation:

  _enrich_services()  (scanning phase, line ~200)
      for each service nmap -sV identified, lookup_cves(product, version)
      -> _findings_from_cves(cves, svc.port, svc.service)
      -> insert_findings_bulk() before the web phase starts

  the web loop      (web phase, line ~790)
      for each web port, check_headers() -> lookup_cves_from_banner(banner)
      -> _findings_from_cves(cves, port, banner)
      -> insert_findings_bulk() per port

Neither knows the other exists. On a host where nmap's product and the
Server header describe the same software, the same CVE arrives twice with
the same port, and both inserts land. The two rows are not byte-identical —
path 1 stores product "Apache httpd", path 2 stores "Apache" — which is why
they read as two findings in the database and why the next section matters.

2.3 The brief's preferred fix was tested against the evidence, and rejected
--------------------------------------------------------------------------------
The brief's option (a) was a shared "already looked up" cache keyed on
product+version, with the second call site skipping the redundant NVD call or
reusing the first result. Scan 140 rules both halves of that out:

  - The keys do not match. nmap reports "Apache httpd"; the Server header
    parses to "Apache" (cve_lookup._parse_banner + _disambiguate_product then
    send "apache http server"). Same software, two different product strings,
    so a product-keyed cache never fires on the very case it was meant for.

  - The second lookup is NOT redundant. It returned three CVEs, of which only
    ONE was the duplicate. CVE-2017-7659 and CVE-2016-4975 came back from the
    header query alone. Skipping the second call, or reusing the first
    result for it, would have silently cost two real HIGH/MEDIUM findings —
    trading a duplicate row for missing vulnerabilities, which is the worse
    defect by a wide margin.

That leaves the brief's own alternative — the CVE id, which is known by the
time a finding exists — and it is also the shape smoke_test7 §3.4 set the
precedent for.

2.4 The fix
--------------------------------------------------------------------------------
modules/profiles/deepscan.py:

    _findings_from_cves(cves, port, service_name, seen=None)

`seen` is a scan-wide set of (cve_id, port) pairs, created once in
run_deepscan() and passed to BOTH call sites. A CVE whose (id, port) pair is
already in the set is not turned into a finding, and says so on the console:

    [*] deepscan CVE-2016-8743 was already recorded on port 80 by an earlier
        lookup — not recorded twice

Deliberately the same shape as _findings_from_nuclei()'s
(template_id, matched_port) guard from smoke_test7 §3.4 — the same problem
(one scan, two paths, one finding) solved the same way, rather than a second
mechanism doing the same job differently. The insert layer (database/db.py)
is untouched; no schema change was needed and none was made.

A CVE that carries no id cannot be keyed and is never dropped by the guard
(t_phase9 §A).

2.5 Safety: the same CVE in a different context still counts twice
--------------------------------------------------------------------------------
The key includes the port precisely so that the fix cannot suppress two
genuinely different findings, which is the failure mode this class of change
risks. Verified (t_phase9 §C):

    same CVE, port 80 and port 8080         -> BOTH recorded
    three different CVEs, one port          -> all three recorded
    same CVE, same port, two lookups        -> one recorded
    two portless copies of one CVE          -> one recorded, and this is the
                                               documented limit of the key:
                                               (cve, None) cannot distinguish
                                               two services with no port

The last line is stated rather than hidden. deepscan always has a port for a
CVE finding (both paths are per-service or per-port), so it does not arise in
practice, but the key would collapse it if it did.

3. PHASE 2 — THE ATTRIBUTION PATTERN, AUDITED CODEBASE-WIDE

3.1 What was audited, and what was found
--------------------------------------------------------------------------------
The §4.2 defect was a classifier deciding "is this a nikto finding?" from a
KEY BEING PRESENT on a dict, on a row read back from SQLite where every
column is present by definition. The audit looked for every other place a
finding's type/tool is decided by anything other than the persisted
finding_type.

Searched: every `"x" in dict` / `.keys()` membership test in modules/,
database/ and aegis.py; every function taking a finding/row; and every
static finding_type -> tool mapping the reports render from.

    key-presence classification, other instances : NONE
        The only two were severity._finding_type and
        remediation._finding_kind, both fixed in smoke_test8. The remaining
        `"in"` hits in the codebase are substring tests on text
        ("legacy protocol" in issue) and PROFILES.keys() in the CLI.

    static mis-attribution                       : TWO (3.2, 3.3)
    untyped rows at the source                   : THREE producers (3.4)

3.2 wordpress_fingerprinted was credited to a tool that never produced it
--------------------------------------------------------------------------------
summary.FINDING_TYPE_TOOL mapped:

    "wordpress_fingerprinted": "wpscan"

That finding is raised by GOBUSTER. gobuster_wrap sets
`wordpress_fingerprinted` when its path sweep hits a /wp-* marker; deepscan
and webaudit both map that flag to the finding. wpscan is what the flag
TRIGGERS afterwards (CONDITIONAL_TOOLS), not what found it — and webaudit
never runs wpscan at all.

Consequence, on both rows that existed before this pass (row 4711, scan 32,
webaudit/daraz.pk; row 5052, scan 88, deepscan/172.28.0.10): every
unpopulated cell on that finding rendered "not determined by wpscan", naming
a tool that had not run. The same defect as §4.2 with a different mechanism:
there the wrong type was inferred, here the right type named the wrong tool.

The webaudit case is the flagrant one — wpscan is not wired into that profile
at all, so the credit could never have been right. In deepscan wpscan may
genuinely run afterwards, triggered by this very finding, which is what made
the mapping look plausible for as long as it did.

    Fixed: "wordpress_fingerprinted": "gobuster".

The finding's remediation text — which advises running wpscan against the
install — is correct and unchanged. Advice to run a tool and credit for
having run it are different claims.

3.3 sslyze findings had no attribution at all
--------------------------------------------------------------------------------
compliance and webaudit both emit `sslyze_finding`, and it was absent from
FINDING_TYPE_TOOL and from every _NOT_APPLICABLE table. An sslyze finding
therefore rendered "not determined" with no tool named, and its CVE/CVSS
cells read as gaps rather than as fields a TLS-configuration finding never
has. No stored row has this type yet (compliance's sslyze pass has produced
no issues on the targets scanned so far), so nothing rendered wrongly — this
is a gap closed before it could, found by the same audit.

    Added: FINDING_TYPE_TOOL["sslyze_finding"] = "sslyze", plus
    cve_id/cvss/version/endpoint/reference N/A entries.

3.4 The root enabler: three profiles were still inserting untyped rows
--------------------------------------------------------------------------------
194 stored findings carry a NULL finding_type today; smoke_test8 §9.7 counted
187 at the time it was written, the difference being rows its own later scans
added. A row with no declared type MUST be classified
by shape when a report reads it — which is the machinery §4.2's bug lived
in. Fixing the classifiers made the guesswork correct; it did not stop the
guessing.

Three insert sites were producing those rows:

    stealth.py:82      insert_findings_bulk(scan_id, open_ports)
    compliance.py:138  findings.extend(open_ports)
    quickscan.py:161   findings = service_result.get("services")

All three now stamp the type at the source — "open_port" for the two nmap
port lists, "service_version" for quickscan's nmap -sV services. Rows written
from here on declare what they are and are never shape-sniffed. Verified live
in §6.2: every finding row written by scans 140-146 carries a finding_type,
and the NULL count across the whole database is still 194 — it stopped
growing rather than being rewritten.

The rendering improves as a side effect, which is the point restated: scan
143's stealthscan row now reads

    Service : http (version N/A (port observation))
    CVE     : N/A (port observation)
    CVSS    : N/A (no CVE to score)

where the same row on scan 134 read "not determined" — the report can now
tell "this field cannot apply here" from "nobody filled this in" because the
row says what it is.

Historical NULL rows are NOT rewritten. They render honestly today (§4.4
shows the attribution check passes on all of them), and rewriting stored scan
history needs the same confirm-first process smoke_test8 §2 used for the
cve_id/cvss backfill.

3.5 The two known classifiers, re-checked under the current schema
--------------------------------------------------------------------------------
Phase 1 added no columns, so the schema they were fixed against is the schema
they run against. Both were re-verified anyway, mechanically:

  - both read finding_type first: a row that declares "open_port" while
    carrying a truthy `reference` classifies as open_port (t_phase9 §F)
  - both agree with each other on every shape tested and on every row in the

4. PHASE 3 — ATTRIBUTION CORRECTNESS AS A TEST CLASS
================================================================================

4.1 modules/reporting/attribution.py
--------------------------------------------------------------------------------
A new module, three checks, run over every row of every scan:

  1. TOOL PLAUSIBILITY   classify the row exactly as a report does, map that
                         kind to the tool(s) that can PRODUCE it
                         (FINDING_TYPE_PRODUCERS), and require at least one
                         of them to be a tool the scan's profile runs
                         (PROFILE_PRODUCERS).

  2. CLASSIFIER AGREEMENT  severity.py and remediation.py must classify the
                         row identically. Documented as one contract since
                         smoke_test8; checked here.

  3. FIELD SIGNATURE     a column summary.py declares inapplicable for a
                         finding type must be NULL on rows of that type, and
                         a type's identity column (a `cve` with no cve_id)
                         must be populated. This is the check aimed at the
                         NEXT shared column: `reference` was added for
                         nikto/ZAP/wpscan and instantly became true of every
                         row; check 3 notices when a new column lands on a
                         finding type that has no business carrying it.

One detail decided the module's correctness. The check classifies
summary._enrich()'s output, not the raw row — _enrich() fills a NULL
description with the derived sentence, and the §4.2 branch could only fire
once a description existed. Checking raw rows would have missed the exact
bug this exists for; that is asserted in t_phase9 §F rather than left as a
comment.

4.2 What a clean sweep does NOT prove
--------------------------------------------------------------------------------
The database stores scans and findings. It does NOT store which tools ran for
a given scan — tool_results lives in memory for the duration of a run and
reaches the reports, not the schema. So check 1 cross-references the set of
tools the scan's PROFILE runs, which is the strongest honest answer available
to "could this tool have produced this row".

    It catches      : a finding credited to a tool the profile never invokes
                      — the whole class §4.2 belongs to, and the class §3.2
                      belonged to.
    It cannot catch : a tool that is wired into the profile but was skipped,
                      failed, or never reached on that particular run.

Persisting a per-scan tools-run record would close that gap and is the
obvious next step; it is a schema change and was not made on the way past.

4.3 Wired into the sweep, not left as a separate step
--------------------------------------------------------------------------------
The whole-database render sweep smoke_test5-8 ran lived in a scratch
directory (/tmp/...), like the test suite before smoke_test8 §8.2 rescued it.
It is now tests/db_sweep.py, in the repository, with the attribution check as
a fourth column of its output:

    python tests/db_sweep.py            # every scan
    python tests/db_sweep.py 141 142    # named scans

    scans rendered      : 144/144
    crashes             : 0
    ambiguous cells     : 0
    dup top-find scans  : 0
    attribution issues  : 0
      of which historical: 2 (known, not counted — see KNOWN_HISTORICAL)

Exit status is non-zero if anything fails, so it is usable as a gate. The
attribution check is not a separate command anyone has to remember, which was
the point: the §4.2 bug survived because the question was nobody's job.

4.4 The current database: two historical rows, reported not corrected
--------------------------------------------------------------------------------
Run across all 144 scans and 6,118 findings, the check reports exactly two
mismatches, both in the project's first two days:

    row 1  scan 1, 2026-07-23 21:50, example.com, profile "quickscan"
           CVE-2021-41773 / CVSS 9.8 / "Apache 2.4.49"
    row 4  scan 3, 2026-07-24 03:33, scanme.nmap.org, profile "quickscan"

8. HONEST LIMITATIONS
================================================================================
 1. The attribution check verifies a finding against the tools its PROFILE
    runs, not against the tools that actually ran on that scan — there is no
    per-scan tools-run record in the schema to check against (§4.2). A
    finding credited to a wired-but-skipped tool would pass.

 2. Two historical rows (1 and 4) remain attribution mismatches and are
    excluded from the sweep's exit status by an explicit, printed allowlist.
    They are wrong in the database and are left that way deliberately (§4.4).

 3. 194 stored rows still carry a NULL finding_type and are still classified
    by shape when rendered. The three producers are fixed (§3.4) so the
    number stops growing, but the existing rows are unchanged and the
    shape-sniffing fallback still exists for them. It cannot be removed while
    they do.

 4. The (cve_id, port) dedup key collapses two CVE findings that share an id
    and have NO port (§2.5). deepscan always records a port for these, so it
    is unreachable today, not impossible in principle.

 5. webaudit has only one CVE-enrichment path (per web port), so it did not
    need and did not get the shared set. If a second path is ever added
    there, the same guard has to be added with it — the attribution sweep
    will not catch a duplicate, only a mis-credit.

 6. §3.3's sslyze fix is verified by unit test and by rendering, not by a
    live sslyze finding: no target scanned so far has produced one.

 7. The repository's venv/ is missing python-owasp-zap-v2.4, which
    requirements.txt lists and the system interpreter has. Scans 140-145 ran
    inside that venv; the two deepscans among them (140, 141) therefore ran
    no ZAP and report "tools failed: 1" (§6.2 — the other three profiles do
    not run ZAP, so they are unaffected). Found by this pass, left as-is
    because installing into someone's virtualenv was not part of the brief,
    and worked around by re-running the verification deepscan under the
    system interpreter (scan 146, 0 failures). Anyone running
    `venv/bin/python aegis.py ... --profile deepscan` today gets one tool
    down.

 8. This pass's live scans all ran against the two local Docker fixtures.
    The duplicate was reproduced on public hosts before (scans 130, 138) and
    the mechanism is target-independent, but no public target was re-scanned
    after the fix.
