Issue #5 — stealthscan/deepscan full-port sweep returns 0 findings
--------------------------------------------------------------------------------
Status: PARTIALLY FIXED — root cause chain fully diagnosed and two of three
contributing bugs are fixed and verified; the third (stealthscan's real-world
completion time) is fixed by reasoning + partial live data, NOT fully
re-verified end-to-end, due to session time constraints. Documented honestly
rather than claimed as done.

This turned out to be three stacked bugs, found only by live-testing (unit/
mocked tests did not and could not catch any of them):

  (a) Original bug (smoke_test1): TOOL_TIMEOUTS['nmap']=300s applied
      uniformly regardless of nmap_args weight. FIXED: run_tool() now accepts
      a timeout override; port_scanner.py computes one dynamically from the
      actual nmap_args.

  (b) A killed nmap process does NOT reliably flush a partial, parseable
      -oX document for a single-host scan — this was an assumption in the
      original fix plan, DISPROVED by direct testing (SIGTERM/SIGINT sent
      after 6s, 20s, and 90s into a live -p- sweep; in every case the -oX
      file still contained only the <scaninfo> header, no <host> data).
      FIXED: replaced "read the killed process's partial file" with
      splitting '-p-' into 32 sequential ~2048-port chunks
      (port_scanner.py:_split_full_range), each a complete, independent nmap
      invocation. A chunk that finishes contributes real results
      immediately; a chunk that times out stops the scan there, keeping
      every earlier chunk's ports. Verified with a mocked test
      (chunk 1 succeeds, chunk 2 times out -> port from chunk 1 is retained,
      not lost) — this mechanism itself works correctly.

  (c) Real-world completion time was badly underestimated, discovered only
      through live calibration against scanme.nmap.org (most of its ports
      are firewall-"filtered", nmap's slowest response class — every filtered
      port needs a full RTT-timeout+retry cycle with no early-out,
      regardless of -T template):
        -T4 (no -sV/-sC)  : ~9.4 ports/sec measured (500 ports in 53s)
        -T2 ("Polite")    : ~0.29 ports/sec measured (500 ports in 1745s =
                            29 minutes) — a full 65535-port sweep at this
                            rate would take an estimated 60+ hours
        -T1 ("Sneaky")    : not separately measured — nmap's own man page
                            states it serialises with a 15-second wait
                            between EVERY probe, and warns T0/T1 "will take
                            an extraordinarily long time to scan thousands
                            of ports." Confirmed consistent with this
                            project's original -T1 -p- chunk (8191 ports)
                            not completing within a 188s budget.
      This directly explains why every single stealthscan run in this
      sweep (both targets) still shows 0 findings: the profile's nmap_args
      were still -T1 at sweep-start time; mid-session this was corrected to
      -T2, which the live data above then also proved impractical; the
      profile now uses -T3 (nmap's own documented default/recommended
      choice for exactly this situation — the man page literally says
      "I normally recommend [-T3] for cautious scanners" after warning
      how slow -T2 really is). NMAP_TIMEOUTS and the per-chunk timeout
      floor were recalibrated from the T4 baseline with a safety margin
      (config.py, port_scanner.py).
      NOT FULLY VERIFIED: a live T3 calibration run was started but not
      allowed to finish before this report was written (user requested
      wrapping up quickly). The fix is well-reasoned (T3 is nmap's own
      documented middle ground, and every other profile's web-scoped
      port lists already work fine) but "stealthscan completes a full
      65535-port sweep against a real target end-to-end" was not watched
      to completion this session. Recommended first action next session:
      re-run stealthscan against scanme.nmap.org and confirm chunk 1
      succeeds (previously: 0/4 attempts succeeded, across -T1, -T2 twice,
      and -T4-without-sV/sC).

Root cause: (a) fixed timeout not scaled to nmap_args; (b) nmap does not
flush usable partial XML on kill for a single-host scan; (c) -T1/-T2 are
architecturally too slow to complete a full port range against a real,
partially-filtered target in any bounded time — this is a target/network
characteristic nmap's own documentation warns about, not a timeout-tuning
problem.

Fix: modules/utils/config.py (NMAP_TIMEOUTS, PROFILES['stealthscan']
nmap_args now -T3), modules/scanning/port_scanner.py (_compute_nmap_timeout,
_split_full_range/_FULL_RANGE_CHUNKS=32, per-chunk timeout floor=300s).

Severity: BLOCKS USAGE for stealthscan specifically (still 0/2 targets
producing findings in this sweep); the underlying chunked-partial-recovery
mechanism is proven correct in isolation, so this is now a calibration/
verification gap, not an architecture gap.

Issue #5b (NEW, found and FIXED this round) — deepscan also returns 0
findings on scanme.nmap.org despite exiting cleanly, no timeout
--------------------------------------------------------------------------------
Status: FIXED AND VERIFIED (re-run live after the fix: scan 73, completed
in 167.2s — chunk 1 still could not complete in this network's real
conditions, since deepscan's discovery pass is now a bare -T4 -p- with the
SAME calibrated-too-tight-for-this-network chunk math as stealthscan; see
Issue #5c below for the honest follow-up this surfaced).

Symptom: scanme.nmap.org's deepscan (scan_id=66) completed in 173s with
exit 0 (not killed, not an error) but persisted 0 findings — unlike
pentest-ground.com's deepscan (scan_id=71), which found 47 in the same
sweep.
  scan_errors.log: "Tool failed: nmap — chunk 1/8 (1-8191) timed out after
  112s — stopping with 0 port(s) recovered from 0 completed chunk(s)"

Root cause: modules/utils/config.py's PROFILES['deepscan']['nmap_args'] was
["-T4", "-p-", "-sV", "-sC"] — combining a full 65535-port sweep with
per-port version detection (-sV) AND nmap's default NSE script suite (-sC)
is nmap's single slowest possible combination. deepscan.py ALSO already ran
a second, separate, correctly-scoped -sV pass via
modules/scanning/service_detect.py against just the discovered open ports —
so the -sV/-sC on the full-range discovery scan was pure, expensive
redundancy that happened to be exactly what pushed every chunk over its
timeout.

Why it's happening: config.py's profile definition never accounted for the
fact that service_detect.py already exists and does this work correctly and
cheaply (scoped to a handful of ports, not 65535 of them).

Fix: PROFILES['deepscan']['nmap_args'] is now just ["-T4", "-p-"] (bare
discovery). modules/scanning/service_detect.py's existing targeted pass now
runs -sV -sC together (was -sV only) and returns a new `scripts` key;
deepscan.py sources its nmap-script findings from that call instead of the
initial full-range scan. Verified: re-running deepscan against
scanme.nmap.org after this fix no longer shows the -sV/-sC-inflated timeout
— chunk 1 now times out for the SAME underlying reason as stealthscan's
Issue #5c (see below), which is real, separate, and already documented
there, not a regression of this fix.

Severity: was BLOCKS USAGE (deepscan silently returning nothing with no
error surfaced to the user); now correctly surfaces as an honest, logged
partial-scan condition instead of a silent redundant-work timeout.

Status: PARTIALLY FIXED — see Issue #5's "(c)" sub-bullet above; this is the

under the corrected numbers, again due to time constraints.

Fix: same config.py/port_scanner.py changes as Issue #5.

Severity: degrades data quality (deepscan's open-port list can come back

Known Issue #1 — no way to skip a single hung tool without aborting the
whole scan; NEW: dedicated skip keybind
--------------------------------------------------------------------------------
Status: NEW FEATURE IMPLEMENTED AND VERIFIED (both paths, via a real
pseudo-TTY, not just a non-interactive no-op check).

Implementation: modules/utils/error_handler.py's run_tool() now runs a
background cbreak-mode listener (config.SKIP_KEY, default 's') alongside
each subprocess. The listener only activates when stdin is a real,
interactive TTY (sys.stdin.isatty()) — inert and side-effect-free for
non-interactive/automated runs (confirmed: this whole 10-run sweep ran
non-interactively with zero listener-related errors or hangs).
config.COMPULSORY_TOOLS names tools that cannot be skipped (nmap, nmap-sV,
nslookup) with the reason why, for downstream-dependency protection.

Verified live via a real pty (python's pty.openpty(), not a mock):
  - Skippable tool: a "sleep 20" tool with timeout=60, skip key pressed at
    3s -> returned {success: False, skipped: True, returncode: -15,
    duration: 3.02s} — the tool was actually terminated early via SIGTERM.
  - Compulsory tool: same test with tool_name="nmap" (in COMPULSORY_TOOLS),
    skip key pressed at 2s -> tool ran to its FULL natural duration (5.0s
    for a "sleep 5"), confirming the skip was correctly ignored with a
    logged/printed reason rather than silently honoured.
Distinct logging added (logger.py:log_tool_skip -> "Tool skipped by user: X"
vs. "Tool failed"/timeout), and the final SCAN SUMMARY panel now shows a
real "Tools skipped by user: N" count.
Not exercised inside this specific 10-run sweep itself (all 10 runs were
non-interactive/automated), by design — the pty tests above are the
verification for this feature; re-running interactively is a good follow-up
but not required to confirm the mechanism works.

New Issue C — nuclei findings with real CVE IDs are not persisted with a
cve_id
--------------------------------------------------------------------------------
Status: NOT FIXED (found late in this pass; documented for follow-up).

Symptom: pentest-ground.com's quickscan (scan 68) surfaced real nuclei
matches with CVE IDs in the console output —
  "[+] [Nuclei]  Redis Lua Parser < 8.2.2 - Use After Free (CVE-2025-49844)"
— but the corresponding DB row has cve_id=NULL. Verified this is a nuclei
detection genuinely worth trusting (4 distinct real 2025 Redis CVEs plus
default-login/unauthenticated-access findings, all CRITICAL/HIGH, consistent

it when a template maps to a CVE); _findings_from_nuclei() in quickscan.py/

Recommended fix: modules/web/nuclei_wrap.py:_parse_nuclei_jsonl() — extract
`obj.get("info", {}).get("classification", {}).get("cve-id")` (a list;
nuclei can map one template to multiple CVEs) into each finding dict, and
thread it through quickscan.py/deepscan.py's _findings_from_nuclei() into
the persisted finding's cve_id field, matching how lookup_cves()'s CVE dicts
already populate it.

Severity: degrades data quality (a real, valuable CVE ID is discovered by
the tool but not queryable/reportable from the database) — cosmetic-to-minor,
not a correctness bug, since the description text still contains the CVE
number as plain text.
