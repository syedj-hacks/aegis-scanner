WHAT THIS DOCUMENT IS
--------------------------------------------------------------------------------
A plain-language snapshot for anyone who wasn't in the room for the last two
fix-and-verify passes (smoke_test1, smoke_test2, smoke_test3): what the
scanner actually does today, what's genuinely solid, what's still a known
gap, and what a professor or external reviewer would notice if they poked
at it live. This is not a sales pitch — where something doesn't work, it
says so.


1. WHAT AEGIS SCANNER IS
================================================================================
A modular Kali Linux vulnerability-assessment CLI (`python3 aegis.py
<target> --profile <profile>`) that wraps ~20 real, industry-standard
security tools behind one consistent framework: a shared subprocess runner
(run_tool()) that never raises and always returns a structured result, a
shared per-target logger, a shared Rich-based terminal renderer, a SQLite
findings database, and three report writers (plain text + PDF + a
self-contained HTML report). Six scan profiles trade off speed, stealth,
and depth:

  quickscan    — fast overview: DNS, top-port nmap, service detection,
                 whatweb + high-severity nuclei
  stealthscan  — quiet, minimal-footprint scan of a curated list of ~20
                 ports that matter (web/mail/db/remote-admin), no service
                 probing, plus ONE whatweb fingerprint on the first open
                 web port. nuclei is deliberately NOT run here — it would
                 make the quietest profile the second-loudest.
  webaudit     — web-focused: headers, nikto, gobuster, whatweb, ZAP
                 baseline, CVE enrichment on discovered web ports
  deepscan     — the full assessment: everything above plus subdomain
                 enum, OSINT, banner grabbing, dirb, nuclei, conditional
                 tools (wpscan/sqlmap/hydra/enum4linux when triggered),
                 CVE/severity/remediation on every finding, TXT+PDF reports
  compliance   — TLS cipher + HTTP header baseline (nmap ssl-enum-ciphers,
                 sslyze, whatweb) on the well-known web/TLS ports
  recon        — PASSIVE attack-surface map: certificate transparency
                 (crt.sh), subdomain enumeration, OSINT, public cloud
                 bucket discovery, and a breach check on harvested email
                 addresses. It sends NOTHING to the target, and it is the
                 only profile that accepts a company NAME as well as a
                 domain ("Acme Corp"). That combination is what makes it
                 safe to point at a name you do not yet have written
                 authorisation to scan.

Every scan persists to database/aegis.db and produces output/<target>/
report_<profile>_<target>_<id>.txt and .pdf, plus a self-contained
report.html, plus a scan_errors.log with a full audit trail of every tool
call, success, failure, timeout, and skip.

Three top-level modes. Running `python3 aegis.py` with no arguments now
asks what you want to do (1 vulnerability scan / 2 recon mapper / 3 scan
diff). ANY argument skips that menu, so every existing command line behaves
exactly as it did before. `--live` opens a browser dashboard that fills in
while the scan runs, served from 127.0.0.1 on a random port.

3. BOTTLENECKS AND KNOWN GAPS (as of 2026-07-25)
================================================================================

3.1 ZAP baseline produced no findings — WAS an environment gap, NOW FIXED
--------------------------------------------------------------------------------
Root cause (confirmed, not guessed): the "Passive scanner rules" ZAP
add-on (the actual ruleset — missing headers, CSP, cookie flags, info
disclosure, vulnerable-JS-library detection, ~60 checks) had been
uninstalled from this machine's ZAP profile. Grepping ZAP's own zap.log
showed it WAS correctly installed and loaded earlier the same day, then
vanished from every later "Installed add-ons" listing with no error
logged against it specifically — while roughly a dozen unrelated add-ons
visibly updated to newer versions in that same window. The likely
mechanism: an add-on auto-update reconciliation (most plausibly triggered
by an earlier `-addonupdate` diagnostic call made while investigating
this very issue) uninstalled the old pscanrules version as part of
updating everything else, then failed to reinstall the replacement
because the marketplace catalog lookup for that specific id kept failing
("Failed to find Add-on: pscanrules") — leaving it permanently
uninstalled instead of restored.

Three narrow in-daemon install attempts (marketplace-by-id, the API's
local-file-install action, the installScannerRules config flag) each
failed for a distinct, confirmed reason and none of them addressed the
actual problem, which wasn't "never installed" but "installed once, then
silently lost." The real fix: `~/.ZAP` is pure local cache/state that
nothing in this codebase depends on persisting, so a fresh copy (full
backup taken first) forces ZAP's own bootstrap to reinstall every bundled
add-on from scratch. Confirmed live: a from-nothing daemon start detected
31 pending add-on updates, downloaded them for real over the network
(let run to completion, NOT killed mid-download — that's the exact
corruption mode this project's own zap_wrap.py design notes already warn
about), came up with 61 real passive-scan rules active, and a clean API
shutdown (`zap.core.shutdown()`) persisted that state for the first time.
A second, independent daemon start afterward loaded all 61 rules again
with no re-bootstrap needed, confirming the fix survives a restart. Then
confirmed end-to-end through the real zap_wrap.py code path (not a
diagnostic script) with real findings on both test targets (see above).

No code changed — this was purely an environment/state fix. One
practical note for whoever next touches this machine: avoid running
`-addonupdate` or a marketplace-based `-addoninstall` against this ZAP
profile casually; that specific action sequence is the leading suspect
for how this got silently broken the first time.

3.2 dirb's default wordlist could re-trip a similar limit on other targets
--------------------------------------------------------------------------------
This session root-caused and fixed dirb's exit-255 failure against
pentest-ground.com (see smoke_test3.txt, Part 2 item 8, for the full
diagnosis): dirb's single-threaded, one-connection-per-request behaviour
was tripping what looks like a connection-count threshold on that specific
target/network path around ~1700 requests into a ~4600-word run. The fix —
defaulting dirb to its own smaller bundled wordlist (959 words) instead of
sharing gobuster's larger one — resolves it for this target and reduces
the same risk generally, but a sufficiently aggressive rate-limiter on a
DIFFERENT target could still trip it at an even lower request count. This
isn't fully eliminated, just made significantly less likely; watch for it
if dirb starts failing again on a new target.

3.3 Full 65535-port sweeps (deepscan's discovery pass) have wide,
    target-dependent variance
--------------------------------------------------------------------------------
deepscan's bare -T4 '-p-' discovery pass is chunked into 32 sequential
sub-scans specifically so a slow/filtered target still yields partial real
results instead of the whole sweep timing out with nothing to show. Against
scanme.nmap.org this session, chunk 1 (the low port range, historically the
slowest because of how many "filtered" ports live there) took ~354-484s
across two measurements, while every subsequent chunk completed in ~7-9s.
Total wall-clock for the full 32-chunk sweep is therefore highly
target-dependent — a network/target with more filtered ports spread across
the whole range would take meaningfully longer than one where only the low
range is slow. This is inherent to nmap's own probing behaviour against a
filtering target, not something the framework can further optimize away
without dropping coverage. Budget deepscan runs generously in a live demo
(don't assume they'll finish in under 2 minutes) or lead with quickscan/
webaudit/compliance/stealthscan, all of which are consistently fast.

3.4 CONDITIONAL_TOOLS (wpscan/sqlmap/hydra/enum4linux) — RESOLVED 2026-07-29:
    all four now observed firing live with real evidence
--------------------------------------------------------------------------------
UPDATE 2026-07-29: this is no longer a gap. These four tools only fire when
their trigger condition is met (WordPress fingerprinted, an injectable
parameter found, a brute-forceable login service open, an SMB port open),
and neither scanme.nmap.org nor pentest-ground.com meets any of them — but
`test-targets/docker-compose.yml` (a local, isolated, intentionally
vulnerable lab on 172.28.0.0/24) does. A full deepscan against each
container produced genuine, evidence-bearing findings with ZERO tool
failures:
  - wpscan   (172.28.0.10, WordPress) — 6 findings: WordPress 7.0.2
    identified, XML-RPC / readme.html / external wp-cron exposure,
    twentytwentyfive theme enumerated
  - sqlmap   (172.28.0.20, DVWA) — CRITICAL boolean-based-blind SQL
    injection on /info.php?id=1, with safe read-only DB enumeration
    (DBMS MariaDB 10.1.26, current database "dvwa", databases listed)
  - hydra    (172.28.0.30, openssh) — weak credential admin:admin found
  - enum4linux (172.28.0.40, samba) — 2 shares + 1 user via null session

Three real bugs were found and fixed while verifying this end-to-end:
  1. wpscan reported nothing on a genuine WordPress site — its wrapper only
     read the (empty, without an API token) vulnerabilities[] arrays. It now
     also surfaces the identified version, enumerated theme/plugins, and
     wpscan's "interesting findings" as LOW/MEDIUM evidence.
  2. nikto hung the full 600s and was killed with zero output — nikto 2.6's
     post-scan "submit to CIRT.net? (y/n)" prompt blocked on stdin even
     under -nointeractive. Fixed with `-ask no` (+ a wider self-terminate
     margin and partial-output salvage). WP and DVWA deepscans both went
     from 1 tool failure to 0.
  3. sqlmap tested only the FIRST discovered .php (usually /index.php, a
     non-injectable redirect) and so missed a genuinely injectable endpoint
     (/info.php) found in the same run. It now probes a ranked, bounded set
     of discovered endpoints (promising names first) and stops at the first
     confirmed injection.

The "condition 'X' not met — skipping Y" scan_errors.log line is still
emitted when a given target legitimately doesn't trigger a tool, so the
"why didn't this run" question stays answerable during a demo.

To reproduce: `cd test-targets && docker-compose up -d`, then
`venv/bin/python3 aegis.py 172.28.0.<10|20|30|40> --profile deepscan`.
See test-targets/README.md for the one-time per-container setup.
(Note: an older revision of this file said to use /usr/bin/python3 because
the venv lacked the zapv2 ZAP client. That is no longer true — the venv has
zapv2 as of 2026-07-29 and deepscans run through venv/bin/python3 with ZAP
active: 61 passive rules, 0 tool failures. Run Aegis through the SAME
interpreter you installed into.)


3.5 NVD CVE version-range false positives — RESOLVED 2026-07-31
--------------------------------------------------------------------------------
Found during the 2026-07-29 verification pass, fixed 2026-07-31. The CVE
enrichment in modules/enrichment/cve_lookup.py filtered NVD results by CPE
*product* but not by CPE *version range*. Because NVD's keywordSearch is a
plain AND-of-words match, a CVE described "before 10.3" was returned — and
reported — against a host running exactly 10.3, i.e. the release that FIXED
it. That produced 7 false-positive CVE findings in one session (5 on the SSH
lab's OpenSSH 10.3, 2 on DVWA's Apache 2.4.25), plus a batch of stale Samba
CVEs matched against Samba 4.12.2 where nmap had only detected the major
version. The CVEs themselves were real; they were misapplied to a version
that isn't vulnerable.

The lookup now reads the vulnerable CPE ranges NVD attaches to each CVE
(versionStartIncluding/Excluding, versionEndIncluding/Excluding) and drops a
CVE only when the detected version is DEFINITIVELY outside every one of them
for the accepted product. Anything ambiguous is kept: no CPE data, a version
wildcard, a detected version too coarse to place against a bound (the bare
"4" vs "before 4.1.22" Samba case above), or no detected version at all. So
the filter can still over-report, but it can never silently hide a real CVE
— the same "cannot verify is not the same as does not match" rule the
product filter already used. Each drop is logged with its count.

Demo note: the earlier advice in §4 to "point at the NVD CVE lookup as proof
it finds real vulns" is safe to use again with this fix in place. Two caveats
worth knowing if a reviewer digs in: (a) a CVE is only as precise as the
version nmap detected — a major-version-only banner keeps borderline CVEs by
design; (b) nuclei-sourced CVEs were accurate even before this fix, because
they are actively detected rather than version-keyword-matched, so they are
the stronger thing to point at if you want a single example.


3.6 Recon mapper — bucket discovery and crt.sh are UNVERIFIED LIVE
--------------------------------------------------------------------------------
Added 2026-08-05. Two of the recon profile's five sources have never actually
produced a result on the development machine, and the honest position is that
those halves are code-complete rather than proven:

  - cloud_enum is NOT INSTALLED here (apt install needs a password this
    session could not supply), so bucket discovery has only ever been
    exercised through its "binary not found on PATH" failure branch.
  - crt.sh returned HTTP 502 on EVERY attempt across two sessions hours
    apart. That is crt.sh's ordinary overload behaviour, not a bug in the
    wrapper, but it means a successful certificate-transparency lookup has
    not been observed here.

What IS verified live: subfinder + amass returned 10,925 real subdomains for
badssl.com in a full run through aegis.py, theHarvester ran, the findings were
scored and persisted, and all three report formats were written. Company-name
mode was verified separately and correctly ran only the two applicable steps.

Both unverified paths fail LOUDLY rather than silently — crt.sh being down is
never rendered as "this domain has no subdomains", and a missing cloud_enum
binary is a reported tool failure. That is what makes this a known gap and not
a silent wrong answer. To close it: `sudo apt install cloud-enum` and re-run.

DO NOT run `pip install cloud-enum` to fix this. That PyPI name is an empty
placeholder package — its own description reads "Reserved name placeholder.
No functionality." — which installs successfully and provides nothing, leaving
the tool apparently installed while the wrapper reports it missing for ever.


3.7 The HIBP breach check needs a paid API key, and says so
--------------------------------------------------------------------------------
Have I Been Pwned has required a paid API key on its breachedaccount endpoint
since 2019. Without AEGIS_HIBP_API_KEY in .env, the recon profile's breach
check reports NOT CHECKED and the summary says so explicitly.

This is worth understanding rather than treating as a missing feature, because
the alternative is the worst possible failure for a security tool. The obvious
implementation treats HTTP 200 as "breached" and everything else as "not
breached" — under which the 401 from a missing key makes every address come
back clean, and the scan reports "0 accounts breached" for an organisation
whose credentials are all over the internet. A false all-clear is the one
output a reader acts on by doing nothing. So "no key" is an explicit
unavailable state here, never a result.

Demo note: if a reviewer asks why this returns nothing, the answer is a
feature, not an excuse — show them the NOT CHECKED line.


3.8 Recon subdomain counts are capped in the report, not in the database
--------------------------------------------------------------------------------
A passive subdomain sweep returns far more than expected: 23,330 unique names
for example.com. Persisting one finding per name produced a report whose real
signal — an open bucket, a breached address — sat at row 12,000, which is to
say no signal at all.

The report therefore lists the 100 best-corroborated names (a name several
sources agree on outranks one only a single source saw) plus ONE summary
finding stating the true total. Every name is still stored in full in the
recon_subdomains table, and the HTML report's recon section shows up to 250
with the true count. Nothing is hidden; the total is always stated.


3.9 The live dashboard stops when the command exits
--------------------------------------------------------------------------------
The --live dashboard is served by a daemon thread inside the scanning process,
so it dies the moment aegis.py returns. An interactive --live run therefore
pauses at the end and waits for Enter, so the completion banner and its link
to the full report are actually reachable; a scripted run prints the path to
report.html instead.

This is a deliberate trade. Making the server outlive the scan would mean
either a non-daemon thread (which would hang every cron/CI run) or a separate
supervised process, and neither is worth it for a view whose whole purpose is
to be watched while the scan happens.

Note also that the dashboard is SERVED over 127.0.0.1 rather than opened as a
file:// page. That is not a preference: browsers block fetch() against file://
origins, so a file-opened dashboard would sit at "waiting for data" for ever
with the reason visible only in the browser console. Nothing is exposed to the
network — it binds loopback only, on an OS-assigned port.


4. IDEAS TO MAKE IT LOOK MORE PROFESSIONAL FOR A DEMO / REVIEW
================================================================================
- Lead the demo with stealthscan, quickscan, or compliance — all three are
  fast (under 3 minutes even on a slow target) and all three now reliably
  produce real, non-zero findings. Save deepscan for a moment where a
  longer wait is acceptable, or kick it off early and let it run in the
  background while narrating the other profiles.
- Show the HTML report (output/<target>/report.html) — as of 2026-08-05 it
  is the strongest single visual the project has. Dark themed, a severity
  donut, and a findings table that sorts by any column and filters by
  severity/type/free text live in front of the reviewer. Worth saying out
  loud while it is open: it is ONE file with no external resources at all,
  so it renders identically offline or as an email attachment — which is
  what a real deliverable has to do.
- Show the PDF report too — it has a proper cover page, a colour-coded
  severity summary with proportional bars, and per-finding cards with
  description/remediation. It reads like a vendor pentest deliverable,
  which is a much stronger visual than a terminal scrollback.
- Run one scan with --live and leave the browser tab visible while it
  works. Watching findings appear in real time, with the current tool and
  a progress bar, demos far better than a static wall of terminal output.
  Start it before you begin narrating, so there is something moving.
- Show the attack-surface delta line that prints after every scan
  ("2 new, 2 fixed since scan #221"), then run the full
  `python3 aegis.py --diff A B`. If you want ONE thing that shows judgment
  rather than plumbing, use the UNVERIFIED category: a finding missing
  from the later scan is only called "fixed" when a tool that would have
  found it actually ran. There is a real pair in the database that reports
  "0 fixed, 71 unverified" where a naive diff would have claimed 71
  remediations. That is the difference between a tool you can act on and
  one you cannot, and it is easy to explain in two sentences.
- `python3 aegis.py --recon "Acme Corp"` is a good opener for a
  non-technical reviewer: it takes a company NAME, touches nothing, and
  explains itself. Pair it with the NOT CHECKED line on the breach check
  (§3.7) as an example of the project refusing to report a false
  all-clear.
- If asked "does this find real vulnerabilities," point at the NVD CVE
  lookup and nuclei findings specifically — those are traceable to a
  public CVE ID or a named, real-world template match, which is more
  convincing than a generic "missing header" finding even though both are
  genuine. The CVE lookup now filters by CPE version range as well as
  product (§3.5), so a "fixed in this exact version" CVE is no longer
  reported against a host running it — but if you want the single
  strongest example, use a nuclei-sourced CVE: those are actively
  detected rather than matched from a version banner.
- ZAP is now a legitimate evidence source too (fixed this session — see
  3.1) — its findings (missing CSP, missing anti-clickjacking header,
  missing SRI attribute, server version disclosure) are a good complement
  to nikto/nuclei/gobuster's since ZAP's passive ruleset catches some
  things those don't.
- If a reviewer asks about wpscan/sqlmap/hydra/enum4linux and the demo
  target doesn't trigger them, the "condition not met" log line (now
  present) is the answer — show it rather than letting it look like the
  tool was silently skipped or forgotten.
- The conditional-tools path (wpscan/sqlmap/hydra/enum4linux) is now
  demonstrable live end-to-end: bring up the local lab in
  `test-targets/` (`docker-compose up -d`) and scan each container's IP
  with deepscan — see §3.4 for the exact targets, the real evidence each
  produced, and the three bugs that were fixed in the process. This was
  the last part of the toolset that had never been observed firing; it
  now has been, with zero tool failures on every one of the four.


5. IF EVIDENCE ISN'T REAL SOMEWHERE — WHAT TO DO
================================================================================
As of this pass, every tool in the toolset that completes without an
error message has been directly observed producing genuine findings this
session or in smoke_test2 (ZAP included, as of this session — see 3.1;
it was the one exception until it got fixed). The general playbook for
treating a scanner's "no findings" result honestly, if this comes up
again with a different tool in the future:
  1. Confirm the tool's own subprocess actually ran and exited cleanly
     (scan_errors.log's "Tool completed: X (duration)" line) — don't
     conflate "completed" with "found something."
  2. Check whether the target genuinely has nothing to find for that
     specific check (a clean, hardened target legitimately produces 0
     nikto findings) versus whether the tool's own ruleset/dictionary/
     signature set is empty or misconfigured (as ZAP's was here).
  3. If unsure, re-run the same tool standalone (bypassing the framework)
     against a target KNOWN to trigger it, and compare. That's exactly
     the method that root-caused (and then fixed) the ZAP gap in this
     pass: it wasn't obvious from a single 0-finding run against one
     target, but became unambiguous once the same 0-finding result
     reproduced identically
     against a second target with genuinely different content.
