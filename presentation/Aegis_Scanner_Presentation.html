What is Aegis Scanner?

You give it a target (hostname or IP) and a profile. It runs a full assessment pipeline and produces a report — with severity, CVEs, and remediation advice.

The key idea

It is not a single scanner. It is an orchestration layer that drives ~18 existing Kali tools, normalises their messy output into one consistent shape, and enriches it.

  • One command instead of 18
  • One consistent report instead of 18 output formats
  • Findings that carry CVE + severity + how to fix

The problem we set out to solve

Doing an assessment by hand is painful

  • Every tool has its own syntax and its own output format
  • You run them one-by-one and copy-paste results together
  • A crashed tool or a Ctrl+C loses everything
  • No single record of "what did we find on this host, and when?"
  • Raw output tells you what — not how bad or how to fix it

What Aegis gives instead

  • One command, one profile, one report
  • Never crashes — every tool failure degrades gracefully
  • Results saved incrementally to a database — an interrupt keeps what was already found
  • Findings graded (CRITICAL→LOW) and paired with remediation text
  • Every scan is history you can diff against later

Organised by layer / phase

The team split the work by layer — each directory is one phase, owned end-to-end. Every module in a phase follows the same shape:

  1. Take a target as input
  2. Call a real tool via run_tool()
  3. Parse output → small predictable dict
  4. Never raise — always return a result

The one rule that holds it together

No module ever calls subprocess directly. Every external tool goes through one gateway: run_tool().

# modules/utils/error_handler.py
def run_tool(target, tool_name, command, timeout=None):
    """Run a CLI tool. Never raises.
    Always returns a structured dict."""
    return {
      "tool": tool_name,
      "success": ...,   # did it work?
      "skipped": ...,   # user pressed 's'?
      "returncode": ...,
      "stdout": ..., "stderr": ...,
      "error": ...,     # human-readable reason
      "duration": ...,
    }

Why it matters

  • One place handles timeouts, the skip key, and Ctrl+C — not 18 copies
  • Popen-based, so a hung tool can be killed mid-flight (SIGTERM → SIGKILL)
  • Pure-Python I/O (sockets, requests) uses the sibling safe_call()
  • A missing binary, unreachable host, or timeout all become the same clean dict — never a stack trace

This is why "never raise, always degrade" is the single most important convention in the codebase.

Layer 2 — Scanning /modules/scanning

port_scanner.py

Drives nmap. A full 65535-port sweep (-p-) is transparently split into 32 sequential chunks.

Why? A killed nmap doesn't reliably flush partial results — so a chunk boundary becomes the real recovery unit. A slow, filtered target still yields partial real results instead of every scan timing out.

service_detect.py

The targeted nmap -sV -sC pass — versions + default NSE scripts. This is where script findings come from.

banner.py

Grabs service banners on non-web ports (a web server sends no unsolicited banner).

hydra_wrap.py

Credential brute-force check — fires only when a login service is detected.

enum4linux_wrap.py

SMB enumeration — shares, users, OS info — when port 445 is open.

Two things worth calling out

  • sqlmap is metadata-only — --banner --current-db --dbs, never --dump/--os-shell. We prove the injection without exfiltrating data.
  • ZAP was rewritten — Kali's apt package doesn't ship zap-baseline.py, so we start ZAP's daemon and drive it over its REST API.

Layer 4 — Enrichment /modules/enrichment

This is where raw tool output becomes an actionable finding. It's what makes Aegis more than a wrapper script.

cve_lookup.py

Takes a Server: Apache/2.4.7 banner, splits it into product + version, queries NVD, and returns matching CVEs.

Two hard-won filters:
1) product disambiguation — a bare "Apache" banner won't match a Groovy RCE.
2) version-range filtering — a CVE fixed "before 10.3" is dropped for a host on 10.3.
Rule: "cannot verify" never means "drop" — it over-reports before it hides.

severity.py

Grades every finding CRITICAL → HIGH → MEDIUM → LOW, preferring a real CVSS score, falling back to keyword heuristics (word-boundary matching, so "rce" doesn't match inside "brute-force").

remediation.py

Attaches a plain-language "how to fix this" line to each finding.

cvss.py

The scoring engine behind severity grading.

Layer 5 — Reporting /modules/reporting

  • summary.py — the shared vocabulary both report writers read from, so TXT and PDF can never describe the same row differently
  • report_txt.py — the plain-text report
  • report_pdf.py — WeasyPrint PDF, with a severity-donut cover drawn as inline SVG (no external assets, no network)
  • retention.py — reports named per-scan and capped, so a new scan never silently overwrites an old one
  • diff.py — compare two scans: what's new, fixed, unchanged
  • attribution.py — the audit layer (next slide)

The database — aegis.db

A single SQLite file that persists scan history across clones. Three tables:

CREATE TABLE scans (          -- one row per run
  id, target, timestamp, profile);

CREATE TABLE findings (       -- what was found
  scan_id, port, service, version,
  cve_id, cvss, severity,
  description, remediation, finding_type,
  parameter, payload, evidence, endpoint,
  reference);

CREATE TABLE scan_tools_run ( -- which tools ran
  scan_id, tool_name, port, outcome);

Design choices

  • Findings are written incrementally — an interrupt keeps what was already found
  • Schema migrates idempotently on every start (add-column-if-missing)
  • scan_tools_run records every tool's outcome so we can later audit: "did the tool this finding is credited to actually run?"

Reliability engineering

A scanner that crashes on a bad target is useless. Three ways a long tool can end early — all handled in one place:

⏱ Timeout

Each tool has a budget. SIGTERM (let nmap flush a partial result) then SIGKILL if it ignores us.

⌨ Skip key

Press s to kill just the current tool and move on. Compulsory tools (nmap, DNS) refuse the skip.

✋ Ctrl+C

Once = skip current tool. Twice within 2s = deliberately abort the whole scan.

Plus a profile-level wall-clock budget

webaudit caps its per-port loop at 30 min, deepscan at 1 hour. When the budget runs out it stops starting new work and finishes with the partial-but-real findings it already has.

Making the output trustworthy

Making a scan work and making its output believable turned out to be two different problems. A report is only useful if you can trust every line.

Every finding says who found it — and we check it

A finding is credited to the tool that produced it. An automated audit (attribution.py + db_sweep.py) re-renders every scan in the database and verifies the credited tool actually ran.

A blank cell is never ambiguous

The report distinguishes "not applicable to this kind of finding" from "a tool should have filled this in and didn't." An empty CVE column on a TLS finding is expected; an empty one on a service finding is a gap.

This caught a real regression where a stealthscan open-port finding was told to "review this nikto finding" — naming a tool that never ran.

Beyond the basics — the "commercial" features

  • Parallelism — web tools and nmap chunks run concurrently; multiple targets scanned at once (proven lossless)
  • Authenticated scanning — --auth-cookie / --auth-header to scan behind a login
  • Multi-target — --targets a.com,b.com or a file, each with its own output dir
  • Scan diffing — --diff 41 57 shows what changed between two runs (perfect for re-tests)
  • CVSS scoring engine + compliance mapping
  • Rate limiting — per-profile throttles so we stay polite / stealthy
  • ZAP in Docker — a reproducible container for the heavy scanner

All shipped on the feature/commercial-upgrade branch with 549 test assertions.

How we know it works

Automated gate

  • tests/db_sweep.py — renders every scan and checks 4 defect classes: crashes, ambiguous cells, duplicate lines, attribution. Exits 0 only when all pass.
  • tests/t_phase*.py — stdlib assertion scripts, one per work pass
  • tests/fixtures/ — real captured tool output, so parser changes are tested against what tools actually print
  • t_pty.py — the skip-key / Ctrl+C paths under a real terminal

Live verification

A local Docker lab (test-targets/) of intentionally vulnerable services — a real WordPress install, an SMB host, a SQLi app — was used to fire the conditional tools with real evidence.

Each verification pass is written up in smoke_test/, ending with an explicit "what's still open" list the next pass opens with.

Hard problems we hit (and solved)

ProblemFix
A killed nmap doesn't flush partial results on a slow target → every scan timed out Split full-port sweeps into 32 chunks; a chunk boundary is the recovery unit
Kali's ZAP package doesn't ship the baseline script Rewrote the wrapper to drive ZAP's own daemon over its REST API
A bare "Apache" banner returned an unrelated Apache Groovy RCE Product disambiguation + CPE allowlist in CVE lookup
CVEs "fixed before 10.3" reported against a host on 10.3 A CVE is dropped only when definitively outside every vulnerable version range
A user skip was miscounted as a tool failure in every profile Every wrapper now threads the skipped flag through
Reports silently overwrote each other Per-scan filenames, history capped per profile+target

Limits & future work

Known, intentional limits

  • deepscan's full-port phase has wide, target-dependent runtime — not a 2-minute demo
  • Conditional tools only fire when their trigger is met (WordPress, SMB, a SQLi param)
  • ZAP isn't reliably interruptible mid-scan — a property of ZAP itself
  • CVE lookup over-reports by design rather than risk hiding a real one

Where it could go next

  • A web dashboard over the SQLite history
  • Scheduled recurring scans + alerting on new findings (diff-driven)
  • More authenticated-scan flows (OAuth, form login)
  • Export to SARIF / ticketing integrations
  • Plugin API so new tools are drop-in wrappers
