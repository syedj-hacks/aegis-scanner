# Aegis Scanner — Study Guide (for me, not the professor)

> Purpose: a plain-language cheat sheet so I know what every file, folder, and concept
> in my project *does* before I present it. Everything here is a few lines, not paragraphs.
> If someone points at any item on screen, this tells me what to say.

---

## 1. The one-sentence pitch
- Aegis is **not a scanner** — it's an **orchestration layer** that drives ~18 existing Kali tools, normalises their output, and enriches it with CVEs + severity + fixes.
- You give it a **target** + a **profile**; it runs recon → scan → web audit → injection checks → enrichment → report.
- The golden rule of the whole codebase: **never crash, always return a result.**

## 3. `aegis.db` — what it is and what's inside
- A single **SQLite database file** = the scanner's memory. It's committed to git, so scan history survives a fresh clone.
- **Three tables:**
  - `scans` → one row per scan run: `id`, `target`, `timestamp`, `profile`.
  - `findings` → what was found: `scan_id`, `port`, `service`, `version`, `cve_id`, `cvss`, `severity`, `description`, `remediation`, `finding_type`, plus injection-evidence columns (`parameter`, `payload`, `evidence`, `endpoint`) and `reference` (a citation link).
  - `scan_tools_run` → which tools ran on each scan: `tool_name`, `port`, `outcome` (ran / skipped / failed). This is what lets us *audit* that a finding's credited tool actually ran.
- Currently holds **~208 scans and ~8,900 findings**.
- Key idea: findings are saved **incrementally** (as each phase finishes), so an interrupt keeps what was already found.
- Schema **migrates itself** on every start — adds any missing column without touching existing rows.

## 4. The layers inside `modules/` (say this per folder)

### `utils/` — the foundation everything sits on
- `error_handler.py` → **the most important file.** `run_tool()` runs every external tool; `safe_call()` wraps every pure-Python call. Both **never raise**, always return a dict, and handle timeout/skip/Ctrl+C in one place.
- `config.py` → all settings: profiles, tool timeouts, rate limits, skip key. (Git-ignored; generated from `config.example.py`.)
- `config.example.py` → the tracked template teammates copy from.
- `logger.py` → structured logging to `output/<target>/scan_errors.log`. No `print()` allowed anywhere else.
- `display.py` → all terminal output (Rich library — the pretty panels, tables, progress bars).
- `auth.py` → loads the credentials for authenticated scans (`--auth-cookie` / `--auth-header`).

### `recon/` — "what does this target expose?"
- `dns.py` → resolves hostname → IPs and records.
- `subdomain.py` → finds subdomains (subfinder / amass).
- `osint.py` → public intel: cert-transparency hosts, emails (theHarvester / crt.sh).

### `scanning/` — ports & services
- `port_scanner.py` → drives nmap. Full 65535-port sweeps are split into **32 chunks** so a slow target still yields partial results.
- `service_detect.py` → the `nmap -sV -sC` pass — versions + default scripts.
- `banner.py` → grabs banners from non-web ports.
- `hydra_wrap.py` → credential brute-force — only when a login service is found.
- `enum4linux_wrap.py` → SMB enumeration (shares/users) — only when port 445 is open.

### `web/` — the biggest layer (12 wrappers)
- Discovery: `gobuster_wrap.py`, `dirb_wrap.py` (hidden paths), `whatweb_wrap.py` (tech fingerprint), `header_check.py` (security headers).
- Vulnerability: `nikto_wrap.py` (misconfig), `nuclei_wrap.py` (template scanner), `zap_wrap.py` (OWASP ZAP via its daemon API).
- Injection & scripting: `sqlmap_wrap.py` (**read-only** SQLi enumeration — never dumps data), `xss_wrap.py` (nuclei in DAST mode, XSS tag).
- TLS / CMS: `sslyze_wrap.py`, `testssl_wrap.py`, `wpscan_wrap.py`.

### `enrichment/` — raw output → actionable finding (what makes us more than a wrapper)
- `cve_lookup.py` → banner → product+version → NVD → matching CVEs. Two smart filters: product disambiguation + version-range filtering. Rule: *"cannot verify" never means "drop."*
- `severity.py` → grades CRITICAL→HIGH→MEDIUM→LOW (CVSS first, then word-boundary keyword matching).
- `remediation.py` → attaches a "how to fix" line to each finding.
- `cvss.py` → the CVSS scoring engine behind severity.
- `compliance_map.py` → maps findings to compliance controls.

### `reporting/` — turning findings into documents
- `summary.py` → the **shared vocabulary** both report writers read from (so TXT and PDF never disagree).
- `report_txt.py` → the plain-text report.
- `report_pdf.py` → the PDF (WeasyPrint) with a severity-donut cover drawn as inline SVG (no network needed).
- `retention.py` → names reports per-scan and caps history, so a new scan never overwrites an old one.
- `diff.py` → compares two scans: new / fixed / unchanged.
- `attribution.py` → the audit layer: checks every finding is credited to a tool that actually ran.
- `completion.py` → the end-of-scan "REPORT GENERATED" banner.

### `profiles/` — the orchestrators (one per scan type)
- `quickscan.py`, `stealth.py`, `webaudit.py`, `deepscan.py`, `compliance.py` → each one decides which tools to call and in what order.
- `_common.py` → shared helpers every profile uses (so logic isn't copy-pasted 5 times). Holds the "did this tool run/skip/fail?" predicate and the end-of-scan report sequence.
- `multi_target.py` → runs a profile against several hosts at once (`--targets`).

## 5. The 5 profiles (know the differences cold)
- **quickscan** (default) → fast: DNS, top-port nmap, service detect, whatweb + high-severity nuclei.
- **stealthscan** → quiet `-T2` scan of ~20 curated ports, minimal footprint, no service-detect pass.
- **webaudit** → full web audit: headers, nikto, gobuster, dirb, whatweb, sslyze, XSS pass, CVE lookup.
- **deepscan** → everything: recon + all 65535 ports + full web audit + ZAP + conditional sqlmap/hydra/wpscan/enum4linux + full enrichment. Slowest.
- **compliance** → TLS ciphers + security-header nmap scripts + sslyze + whatweb. No DNS step.
- All five produce **both** a TXT and a PDF report.

## 6. How we reached the final scanner (the story arc)
1. **Foundation first** — built the `run_tool()` / `safe_call()` gateway and the "never raise" rule. Everything else depends on it.
2. **Layer by layer** — recon, then scanning, then web, each phase owned by a teammate, each module the same shape.
3. **Made it reliable** — added the skip key, a saner Ctrl+C, chunked nmap sweeps, per-port incremental saving, and wall-clock budgets. Goal: survive a slow/broken target.
4. **Made injection first-class** — dedicated sqlmap (read-only) + XSS wrappers that carry real payload evidence.
5. **Made the output trustworthy** — this was a *separate* problem from making it work. Added per-scan report naming, the "not applicable vs. genuine gap" distinction, and the `attribution.py` audit that re-checks every finding against which tools actually ran.
6. **Recorded what ran** — the `scan_tools_run` table, so the audit can ask "did this tool run on *this* scan," not just "does this profile normally use it."
7. **Commercial upgrade** — parallelism, authenticated scanning, multi-target, scan diffing, a CVSS engine, compliance mapping, rate limits, ZAP-in-Docker. (549 test assertions.)
8. **Verified live** — a Docker lab of vulnerable targets fired every conditional tool with real evidence; each pass written up in `smoke_test/`.

## 7. Concepts I should be ready to define
- **Orchestration layer** → software that coordinates other tools rather than doing the work itself.
- **Wrapper module** → a small file that runs one external tool and returns its output as a clean dict.
- **Profile** → a named bundle of "which tools to run, how aggressively."
- **Finding** → one result: a port, a CVE, a vulnerability — with severity + remediation.
- **Enrichment** → adding context (CVE, severity, fix) to a raw result.
- **Attribution** → verifying each finding is credited to the tool that actually produced it.
- **NVD** → the U.S. National Vulnerability Database — where we look up CVEs.
- **CVE / CVSS** → a CVE is a specific vulnerability ID; CVSS is its 0–10 severity score.
- **DAST** → Dynamic Application Security Testing — testing a running app (how our XSS/nuclei checks work).
- **Idempotent migration** → a schema update safe to run repeatedly; it only adds what's missing.
- **Incremental persistence** → saving results as you go, not all at the end, so an interrupt loses nothing.
